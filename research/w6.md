## d1 FlashAttention 1 to 4
- FA1 https://arxiv.org/abs/2205.14135: "We propose FlashAttention, an IO-aware exact attention algorithm that uses tiling to reduce the number of memory reads/writes between GPU high bandwidth memory (HBM) and GPU on-chip SRAM." / "15% end-to-end wall-clock speedup on BERT-large (seq. length 512) compared to the MLPerf 1.1 training speed record, 3× speedup on GPT-2 (seq. length 1K), and 2.4× speedup on long-range arena (seq. length 1K-4K)."
- FA2 https://arxiv.org/abs/2307.08691: "FlashAttention is still not nearly as fast as optimized matrix-multiply (GEMM) operations, reaching only 25-40% of the theoretical maximum FLOPs/s." / "suboptimal work partitioning between different thread blocks and warps" / "(1) tweak the algorithm to reduce the number of non-matmul FLOPs (2) parallelize the attention computation, even for a single head, across different thread blocks to increase occupancy, and (3) within each thread block, distribute the work between warps to reduce communication through shared memory." / "around 2× speedup compared to FlashAttention, reaching 50-73% of the theoretical maximum FLOPs/s on A100" / "up to 225 TFLOPs/s per A100 GPU (72% model FLOPs utilization)".
- FA3 https://arxiv.org/abs/2407.08608: "FlashAttention-2 achieving only 35% utilization on the H100 GPU." / "exploiting asynchrony of the Tensor Cores and TMA to (1) overlap overall computation and data movement via warp-specialization and (2) interleave block-wise matmul and softmax operations, and (3) block quantization and incoherent processing that leverages hardware support for FP8 low-precision." / "speedup on H100 GPUs by 1.5-2.0× with FP16 reaching up to 740 TFLOPs/s (75% utilization), and with FP8 reaching close to 1.2 PFLOPs/s." / "FP8 FlashAttention-3 achieves 2.6× lower numerical error than a baseline FP8 attention."
- FA4 (MLSys 2026; Zadouri, Hoehnerbach, Shah, Thakkar, Dao) https://proceedings.mlsys.org/paper_files/paper/2026/file/ae8b0b5838ba510daff1198474e7b984-Paper-Conference.pdf: "tensor core throughput doubles while other functional units (shared memory bandwidth, exponential units) scale more slowly or remain unchanged." / "(1) redesigned pipelines that exploit fully asynchronous MMA operations and larger tile sizes, (2) software-emulated exponential and conditional softmax rescaling that reduces non-matmul operations, and (3) leveraging tensor memory and the 2-CTA MMA mode to reduce shared memory traffic and atomic adds in the backward pass." / "up to 1.3× speedup over cuDNN 9.13 and 2.7× over Triton on B200 GPUs with BF16, reaching up to 1613 TFLOPs/s (71% utilization)." / "implement FlashAttention-4 entirely in CuTe-DSL embedded in Python, achieving 20-30× faster compile times compared to traditional C++ template-based approaches" / "While FlashAttention-3 optimized attention for Hopper GPUs through asynchronous execution and warp specialization, it primarily targets the H100 architecture." Body: "FA4 achieves 1.1-1.3× speedup over cuDNN 9.13.0 and 2.1-2.7× over Triton across sequence lengths".

## d2 Megakernels
- Hazy "No Bubbles" https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles (Spector, Juravsky, Sul, Dugan, Lim, Fu, Arora, Ré): "Figure 1: Speed! Results generated with a 32-token prompt and 128 generated tokens, with no speculation" / "on an H100, we use 78% of memory bandwidth and outperform existing systems by over 1.5x. (To our knowledge, this is the lowest-latency forward pass for Llama-1B in bfloat16!)" / "vLLM and SGLang – are only able to use at most 50% of available GPU bandwidth when running this workload on an H100." / "existing systems break down a model forward pass into around a hundred separate kernels" / "In principle, NVIDIA's CUDA graphs can help hide costs, but by our measurements they still leave a lot on the table." / "On an H100, our megakernel runs almost 2.5x faster than vLLM and over 1.5x faster than SGLang. On a B200, the gap with vLLM rises to over 3.5x, and we remain more than 1.5x faster than SGLang, too." / "Our B200 implementation pushes this even further to under 680 microseconds per forward pass!" / "if a kernel runs 512 thread blocks (like our Llama-1B down projection), but we only have 148 streaming multiprocessors (like on a B200), we end up with 80 empty SM's at the end."
- PDL reconstruction https://github.com/tie-pilot-qxw/pdl-megakernel-reconstruction: "On an NVIDIA H100, an 81-kernel CUDA Graph using Programmatic Dependent Launch (PDL) reaches 97.4% of the matched persistent megakernel's end-to-end throughput for the P32/D128 Llama-3.2-1B decode workload." Table: Persistent VM 983.127 us; 81-kernel PDL chain 1009.711 us; Default-dependency chain 1169.071 us. "the PDL chain recovers 85.7% of the gap from the default-dependency chain to the persistent path and finishes within 2.704% of the persistent path." / "CUDA 13.1's H100 ptxas rejects the VM kernel's `setmaxnreg` instructions."
- FlashFormer https://arxiv.org/abs/2505.22758 (MIT): "FlashFormer fuses the entire transformer forward pass into a single kernel for accelerating low-batch inference of large language models." / "On unquantized Llama 3.1 8B, we find that our kernel achieves a 8-20% speedup over GPTFast, and up to a 61% speedup over vLLM." / "The results, shown in Table 6, are small improvements (2%) at short sequence lengths increasing to 13% at longer sequence lengths." (70B) / "Our work is limited insofar as we target the single-GPU, low-batch setting for the Hopper family of architectures."
- Fleet https://arxiv.org/abs/2604.15379 (AMD MI350): "On AMD Instinct MI350 with Qwen3-8B, Fleet achieves 1.3-1.5x lower decode latency than vLLM at batch sizes 1-8" / "Fleet (M-tile) remains 1.06× faster at bs=32 but is slower at bs=64" / "we consider this an inherent tradeoff of the megakernel approach".
- MPK https://arxiv.org/abs/2512.22219: "MPK significantly outperforms existing kernel-per-operator LLM serving systems, achieving up to 1.7× lower end-to-end inference latency".
- Secondary (report.md): "The win regime is narrow and every builder admits it: **memory-bound, batch-1/low-batch, short context, small dense models, latency-critical**." / "**Real deltas vs strong fused baselines: 1.0-1.25x.** The 2-18x academic headlines are baseline choice." / Cursor MoK "2.37x" microbenchmark vs "1.41x" production on 512 GPUs (not read).

## d3 Serving kernels
- FlashInfer README https://github.com/flashinfer-ai/flashinfer: "FlashInfer is a library and kernel generator for inference that delivers state-of-the-art performance across diverse GPU architectures. It provides unified APIs for attention, GEMM, and MoE operations with multiple backend implementations including FlashAttention-2/3, cuDNN, CUTLASS, and TensorRT-LLM." / Adoption: "SGLang, vLLM, TensorRT-LLM, TGI (Text Generation Inference), MLC-LLM, LightLLM, lorax, ScaleLLM". Paper https://arxiv.org/abs/2501.01005: "FlashInfer achieve 29-69% inter-token-latency reduction compared to compiler backends for LLM serving benchmark, 28-30% latency reduction for long-context inference, and 13-17% speedup for LLM serving with parallel generation." / "FlashInfer tackles KV-cache storage heterogeneity using block-sparse format and composable formats".
- Marlin README: "close to ideal (4x) speedups up to batchsizes of 16-32 tokens (in contrast to the 1-2 tokens of prior work with comparable speedup)." / "While existing kernels achieve relatively close to the optimal 3.87x (note the 0.125 bits storage overhead of the group scales) speedup at batchsize 1, their performance degrades quickly as the number of inputs is increased." / "a large matrix that can be ideally partioned on an NVIDIA A10 GPU" / "the kernel's PTX assembly was extensively analyzed in NSight-Compute". Paper https://arxiv.org/abs/2408.11743: "batchsizes up to 16-32 can be supported with close to maximum (4×) quantization speedup, and larger batchsizes up to 64-128 with gradually decreasing, but still significant, acceleration." / "end-to-end LLM inference speedups (of up to 2.8×) when integrated with the popular vLLM serving engine."
- Machete https://developers.redhat.com/articles/2024/10/14/introducing-machete-mixed-input-gemm-kernel-optimized-nvidia-hopper-gpus: "This kernel is the spiritual successor to the Marlin kernels created by Elias Frantar and integrated into vLLM by Neural Magic. While Marlin was specifically designed for Ampere generation GPUs and struggles on Hopper GPUs (namely H100), Machete was built on top of the work highlighted in CUTLASS 3.5.1" / "4bit Llama 3.1 70B on a single H100. In the higher user requests rates (3+ req/s), we see a geomean speedup of 29% for input token throughput and 32% for output token throughput." / "4bit Llama 3.1 405b on 4 H100s ... geomean speedup of 42%".

## d4 Linear attention on NVIDIA
- FlashQLA README https://github.com/QwenLM/FlashQLA: "FlashQLA is a high-performance linear attention kernel library built on TileLang. FlashQLA applies reasonable operator fusion and performance optimization to the forward and backward passes of GDN Chunked Prefill, achieving 2-3× forward speedup and 2× backward speedup over the FLA Triton kernel across multiple scenarios on NVIDIA Hopper and Blackwell." / "[2026-07] ... now serves as a backend for flash-linear-attention's GDN". Benchmark file (H200, Qwen3.5 family, cudagraph; torch 2.8.0, fla 0.5.1, flashinfer 0.6.13, tilelang 0.1.12): `397B/122B TP8 1x32768 ... 0.348ms 1.645ms 1.019ms 2.93x 4.73x` / `1x4096 ... 0.123ms 0.209ms 0.147ms 1.19x 1.70x` / `1x2048 ... 0.066ms 0.108ms 0.088ms 1.32x 1.63x` / `4096x8 ... 0.200ms 0.200ms 0.516ms 2.58x 1.00x` / `1024x8 ... 0.059ms 0.057ms 0.141ms 2.39x 0.97x`.
- FLA README https://github.com/fla-org/flash-linear-attention: "We compare our Triton-based implementations (`chunk_retention`, `chunk_gla`, `chunk_gdn`) with CUDA-based FlashAttention2 across various shape configurations. These tests were conducted on a single NVIDIA GB200 GPU (CUDA 12.9, PyTorch 2.9.0)." Forward B=1, T=8192, H=96, D=128 (ms): `chunk_retention 0.787`, `chunk_gla 1.765`, `chunk_gdn 1.265`, `flash_attn 3.753` (≈3x, agent arithmetic). "[2026-04] Add TileLang backend support for selected kernels", "[2026-07] Add a Gluon backend for AttnRes".
- Gated DeltaNet https://arxiv.org/html/2412.06464v1: "we introduce the gated delta rule and develop a parallel training algorithm optimized for modern hardware." / Fig. 3 "Training throughput comparison of 1.3B models on a single H100 GPU." / "the proposed gated delta rule introduces only marginal overhead compared to the original delta rule, with Gated DeltaNet achieving essentially the same throughput as DeltaNet. Both are slightly slower than Mamba2 (2-3K tokens/sec) due to their more expressive transition matrices." / "The Transformer++ achieves the best performance in the 2K context window domain, thanks to the highly optimized Flash-Attention-2 kernel".
- Kimi Linear https://arxiv.org/html/2510.26692v1: "reducing KV cache usage by up to 75% and achieving up to 6 times decoding throughput for a 1M context." / "the operator efficiency of KDA improves by roughly 100% compared to the DPLR formulation." / "This enables larger batches, yielding a faster TPOT (1.84ms vs. 11.48ms) than MLA at 1M tokens." / "Kimi Linear introduces negligible latency overhead compared to GDN-H during prefilling." / "we open-source the KDA kernel and vLLM implementations" (in FLA at fla/ops/kda).

## d5 Profiling and AI kernels on NVIDIA
- Nsight Compute Profiling Guide https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html: "Collection of performance metrics is the key feature of NVIDIA Nsight Compute. Since there is a huge list of metrics available, it is often easier to use some of the tool's pre-defined sets or sections to collect a commonly used subset." / SpeedOfLight: "High-level overview of the throughput for compute and memory resources of the GPU. For each unit, the throughput reports the achieved percentage of utilization with respect to the theoretical maximum." / "Only focus on stalls if the schedulers fail to issue every cycle." / "In Kernel Replay, all metrics requested for a specific kernel instance in NVIDIA Nsight Compute are grouped into one or more passes."
- KernelBench: "a suite of 250 carefully selected PyTorch ML workloads." / "fast_p, which measures the percentage of generated kernels that are functionally correct and offer a speedup greater than an adjustable threshold p over baseline." / "matching the PyTorch baseline in less than 20% of the cases."
- Stanford CRFM https://crfm.stanford.edu/2025/05/28/fast-kernels.html: "We have some very fast AI-generated kernels in pure CUDA-C without using libraries and DSLs such as CUTLASS and Triton." / "Matmul (FP32): 101.3% performance of FP32 torch.matmul"; "Conv2D: 179.9%"; "Softmax: 111.8%"; "LayerNorm: 484.4%"; "Conv2D + ReLU + MaxPool: 290.1% performance of FP32 torch reference, 189.0% performance of FP32 torch.compile() reference" / "(Our results are benchmarked on an Nvidia L40S GPU, and % performance is defined as reference time divided by generated kernel time)" / FP32 caveat / "through searching we've been steadily increasing the performance of flash attention from <1%".
- SOL-ExecBench README https://github.com/nvidia/sol-execbench and paper https://arxiv.org/abs/2603.19173: "Speed-Of-Light ExecBench is a rigorous GPU kernel evaluation and benchmarking framework built to benchmark AI-generated kernel solutions" / "SOL-Score: a metric that grades custom kernel performance based on the theoretical roofline of a NVIDIA B200 GPU" / "a benchmark of 235 CUDA kernel optimization problems extracted from 124 production and emerging AI models ... targeting NVIDIA Blackwell GPUs." / "progress is constrained by benchmarks that reward speedup over software baselines rather than proximity to hardware-efficient execution." / "sandboxed harness with GPU clock locking, L2 cache clearing, isolated subprocess execution, and static analysis based checks against common reward-hacking strategies."
- AutoKernel https://arxiv.org/abs/2603.21331 (RightNow AI; README "Inspired by @karpathy/autoresearch"): "On an NVIDIA H100, our Triton kernels outperform both PyTorch eager and torch.compile (max-autotune) on the majority of tested configurations: 5.29x over eager on RMSNorm, 2.82x on softmax, and 2.21x on cross-entropy, while beating torch.compile by 2.83x, 3.44x, and 2.94x respectively." / "an AutoKernel-optimized kernel achieved first place on the vectorsum_v2 B200 leaderboard." Secondary (rywalker.com): "matmul is a weak spot at ~28% of cuBLAS throughput".
- GPU MODE KernelBot data https://huggingface.co/datasets/GPUMODE/kernelbot-data: "This dataset contains GPU kernel submissions from the KernelBot competition platform." Secondary (report.md): "KernelBench-Mega's first sweep produced zero true megakernels in 36 submissions — the famous '19.4x' cell was 9 Triton kernels under a CUDA graph, audited and rejected."
