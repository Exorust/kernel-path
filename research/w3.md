## d2 MLX steel and the M5 neural accelerators
- PR #3018 "Add NAX Split-K GEMM for large-K matmuls to improve performance" (hxu296, opened 2026-01-19, merged 2026-01-26) https://github.com/ml-explore/mlx/pull/3018: "Adds NAX Split-K GEMM support to address high runtime variance and slow tail cases in large-K matmals on M5 GPU. For GEMMs with very large K dimensions, partitioning work along K substantially reduces variance and eliminates slow tail cases, achieving up to ~1.6× speedup over the fused NAX GEMM." / "New kernel `steel_gemm_splitk_nax` partitions K-dimension work across threadgroups, then accumulates partial sums" / "Dispatch heuristic: batch_size==1 AND M×N >= 2048^2 AND K >= 10240 AND K >= 3×max(M,N) AND NAX available" / bf16 " 2048  2048  10240    156.11ms    142.52ms      1.10x" … " 4096  6144  21504   2807.22ms   1734.34ms      1.62x" … " 6144  6144  21504   4078.63ms   2635.42ms      1.55x" / fp32 " 2048  2048  10240    193.15ms    196.28ms      0.98x" … " 6144  6144  21504   6762.67ms   4345.39ms      1.56x" / "Some dispatch thresholds (i.e. M×N >= 2048^2 AND K >= 10240) and split_k_partition_size (3072) are empirically determined on M5 GPU."
- Apple M5 newsroom: "M5 introduces a next-generation 10-core GPU architecture with a Neural Accelerator in each core, enabling GPU-based AI workloads to run dramatically faster, with over 4x the peak GPU compute performance compared to M4." / "a nearly 30 percent increase in unified memory bandwidth to 153GB/s" / "Developers can also build solutions for their apps by directly programming the Neural Accelerators using Tensor APIs in Metal 4."
- MPP guide §4.1: "GEMMs have M * N * K multiply add operations with (M * K) + (N * K) input elements and M * N output elements. Hence, the arithmetic intensity is given by: (M * N * K) / ((M * K) + (N * K)) == (M * N) / (M + N) ops per input element and (M * N * K) / (M * N) == K ops per output element" / "In reality, achieving good cache hit rates requires a carefully tiled implementation".
- PR #4237 "Fix M5 split-K NAX dispatch cliff" (PhilipJohnBasile, 2026-08-13, CLOSED not merged): "Across all 33 affected M<=32 cells, speedup was **1.22–1.49x** (median **1.37x**). ## d3 Linear attention on MLX
- mlx-lm PR #1241 "feat: chunked prefill for GatedDeltaNet (FlashQLA algorithm)" (0xClandestine, 2026-05-03, self-closed same day): "Replaces the sequential `gated_delta_ops` Python loop (O(T) dispatch overhead) with a parallel chunked prefill for Qwen3.5/3.6 linear attention layers" / "Measured on Apple M-series (float32, chunk\_size=64, Qwen3.5 config: Hk=16, Hv=64, K=V=128):" / "| 512 | ~200 Ktok/s | ~290 Ktok/s | 1.5× |" / "| 2048 | ~50 Ktok/s | ~340 Ktok/s | 6.8× |" / "| 8192 | ~12 Ktok/s | ~340 Ktok/s | 28× |" / "| 16384 | ~6 Ktok/s | ~340 Ktok/s | 56× |" / closing: "Closing: the existing gated_delta_kernel already handles prefill in a single Metal dispatch with recurrent state in thread registers, which is faster on Apple Silicon than the chunked FlashQLA algorithm (which is optimized for CUDA/Triton). Benchmarks show the existing implementation outperforms this approach for T ≥ 1024. No regression fix needed."
- mlx-lm PR #1559 "Add packed gated delta kernel, bitwise-pinned by an explicit-tree comparator" (wyanzhao, opened 2026-07-13, merged 2026-08-27): "The existing gated-delta prefill kernel assigns one full 32-lane SIMD-group to each value row. ## d5 Launch overhead at scale
- Hazy Research "No Bubbles" (2025-05-27) https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles: "for single-sequence generation in 16-bit precision on a single H100, the memory limit is 3.35TB/s / 2.48GB = ~1350 forward passes per second. But with 7 kernel launches per layer, and 16 layers, even with an optimistic 5 us of stalling per kernel (counting stragglers, kernel launch, and memory latencies), generation would run at just ~770 forward passes per second." / "existing systems break down a model forward pass into around a hundred separate kernels that each implement a few operations (e.g. RMS norm, attention, an MLP layer + activation, rotary)." / "running on a CUDA stream incurs a launch cost of about 2.1 microseconds, and with CUDA graphs the launch cost only decreases to around 1.3 microseconds" / "on an H100, we use 78% of memory bandwidth and outperform existing systems by over 1.5x." Secondary (~/myproj/megakernels-research/report.md): 81-kernel CUDA Graphs + PDL reconstruction reached "97.4% of the megakernel's performance"; "all serious megakernel baselines (vLLM/SGLang) already use CUDA Graphs; the megakernel wins are *on top of* graphs."
- MLX PR #4562 "metal: runtime setter for command-buffer limits" (aidiffuser, 2026-09-25, NOT merged): "MLX commits a command buffer after `max_ops_per_buffer` operations or `max_mb_per_buffer` MB of distinct inputs: 50 / 50 on M3 Ultra ... **Weights count toward the MB budget.** A batch-1 decode step of a large mixture-of-experts model therefore commits after nearly every expert matmul, while `eval` lets at most 10 command buffers be in flight." / "~231 command buffers per decode token, each covering ~0.25 ms of GPU work, so the in-flight window is only ~2.5 ms of lookahead; the GPU busy only 68% of the time at 123k context." / "| | 123k | 15.4 → 18.1 (+17.5%) |" (GLM-5.3 744B 4-bit, two M3 Ultra Mac Studios, tensor-parallel) / "**GLM-5.3 at 123k:** GPU busy 83 → 89%, and command buffers per 4 s fell from 24,107 to 2,925." / "A 30k-token prefill then held **+88 GB instead of +8 GB**."
- MLX compile docs https://ml-explore.github.io/mlx/build/html/usage/compile.html: "If you use this function with small arrays, it will be overhead bound. If you use it with large arrays it will be memory bandwidth bound. However, all of the operations in the gelu are fusible into a single kernel with compile() ." / "On an M1 Max the times are 15.5 and 3.1 milliseconds. The compiled gelu is five times faster."
- llama.cpp: PR #1860 "metal : parallel command buffer encoding" (merged 2023-06-15): "Use multiple command buffers - Enqueue them at start - Encode the commands in parallel on separate threads ... On M1 Pro there is no difference in the measured inference time." PR #15929 "metal : allow ops to run concurrently" (merged 2025-09-13): "keep track of the memory intervals/ranges from which we read data and to which we write data. Using this information, for the new node we can determine if it can safely run concurrently with all the concurrent ops prior to it" / "The benefits are large for TG and decent for PP." / "| gemma3 270M Q4_0      | tg128  |       333.98 |                           392.28 |      1.17 |" / "| gpt-oss 20B MXFP4 MoE | tg128  |       120.91 |                           133.14 |      1.10 |". #19555 "metal : improve concurrency" (merged 2026-02-13): ~0.98–1.04x.
