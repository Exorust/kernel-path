## d2 The GPU core
Sources:
1. Tech talk "Explore GPU advancements in M3 and A17 Pro" https://developer.apple.com/videos/play/tech-talks/111375/ (4:46–16:10) — [531s] "The number of SIMDgroups that are concurrently running on a shader core is called its thread occupancy." [593s] "Prior to the Apple family 9 GPU, a SIMDgroup could not begin execution on a shader core until it allocated registers from the on-chip register file. … The amount allocated would be equal to the maximum register usage at any point in the program." [645s] "On-chip register memory is now dynamically allocated and deallocated over the lifetime of the shader according to what each part of the program actually uses." [682s] "because the register file is now a cache instead of the permanent storage for the registers" [695s] "The flexible on-chip memory feature extends this treatment to the rest of the shader core's memory types, such as threadgroup and tile memory, making that a cache too." [713s] "redesign the on-chip memories into fewer larger caches that service all these memory types." [796s] "the shader core will dynamically monitor your shaker's [sic] behavior and adjust the occupancy level" [823s] "you, the developer, need to optimize occupancy a lot less often than in the past."
2. philipturner/metal-benchmarks README (634 stars, last push 2024-09-22; M1/M2 data): https://github.com/philipturner/metal-benchmarks — "| Register File | ~208 KB |" / "| Shared Memory | ~60 KB |" / "| Data Cache | 8 KB |" / "| Instruction Cache | 12 KB |" / "| Global Cache Line | 128 B |" / "The Apple GPU core has four schedulers, each dispatching one instruction from one simd (32 threads) per cycle." / "Apple GPUs have much smaller data caches than other vendors. The L1 is 8 KB … The M1 started with 768 KB, then shot down to 256 KB for the M1 Pro." / "The larger register size makes up for the smaller lower-level cache sizes." / "On bandwidth bound tasks, the GPU has no advantage over the CPU. Some matrix blocks could remain locally accessible to only one SIMD-group, while other blocks are temporarily shuffled into the narrow threadgroup memory."

## d3 Metal
Sources:
1. "Performing Calculations on a GPU" https://developer.apple.com/documentation/metal/performing-calculations-on-a-gpu — "MSL is a variant of C++ designed for GPU programming." / "Metal creates a `MTLDevice` for each GPU." / "When you build the app, Xcode compiles the `add_arrays` function and adds it to a default Metal library that it embeds in the app." / "The function object is a proxy for the MSL function, but it's not executable code. You convert the function into executable code by creating a pipeline." / "When you create a pipeline state object, the device object finishes compiling the function for this specific GPU." / "To send work to the GPU, you need a command queue." / "The sample app uses shared memory (), which both the CPU and GPU can access." / "Ask the command queue to create a command buffer." / "This sample creates a compute command encoder, which encodes a compute pass." / "Metal subdivides the grid into smaller grids called threadgroups." / "Run the commands in the command buffer by committing the command buffer to the queue." / "After you commit the command buffer, Metal asynchronously prepares the commands for execution"
2. MSL spec 4.1 https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf — "In Metal 4 and later, the Metal programming language is a C++17-based specification with extensions and restrictions. … Prior language versions of Metal are a C++14-based specification with extensions and restrictions." / "All OS: Metal 2.3 and later support SIMD-group matrix types. Metal supports a matrix type simdgroup_matrix<T,Cols,Rows> … Operations on SIMD-group matrices are executed cooperatively by threads in the SIMD-group." / "where T is half, bfloat (in Metal 3.1 and later) or float and Cols and Rows are 8". Section 7 is "Metal Performance Primitives" ("Table 7.4. MatMul2D descriptor parameters").
3. MPP Programming Guide v1, 2026-03-16 https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf — "Metal 4 introduces the tensor resource and the Metal Performance Primitives (MPP) framework for authoring machine learning kernels that leverage GPU neural accelerators in the Apple M5 chip." / "The mpp::tensor_ops APIs contain a library of compute primitives you can use inside a kernel to invoke threadgroup- or simdgroup-scoped operations on tensors." / "Theadgroup [sic] memory staging isn't necessary for the most optimized GEMM kernels. The on-chip memory hierarchy works best when you directly access device memory and allow the different levels of caching to work as designed." / "Kernels don't require any explicit software pipelining to overlap memory and compute operations. Metal achieves this execution overlap naturally with sufficient thread occupancy on each core." / "On the M5 chip, a 2 x 2 tile of simdgroups per threadgroup is a good starting point for 16-bit floating-point operands" / "On the M5 chip, SM == SN == 32 is a good starting point for 16-bit floating-point operands"
4. Tech talk 10580 — [134s] "The top layer is the command queue." [143s] "The commands are batched up on the CPU through a command buffer."
