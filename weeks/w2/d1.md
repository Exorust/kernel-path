# Week 2, day 1 · Roofline on Apple

**Why this day.** Every kernel family this week and every speedup story next week is a point on one chart. The roofline is the chart. If you can place a kernel on it before running, you can predict its time, and you can tell an AI what to aim for.

## The story

The roofline model was named in a 2008 paper by Williams, Waterman, and Patterson. It needs one number about the kernel and two about the machine. The kernel's number is "operational intensity", defined as "operations per byte of DRAM traffic". The machine's numbers are its peak compute and its peak memory bandwidth. The model is one line: "Attainable GFlops/sec = Min(Peak Floating Point Performance, Peak Memory Bandwidth x Operational Intensity)" ([Williams et al.](https://users.cs.duke.edu/~lkw34/papers/roofline-cacm2008.pdf)). Plotted, it is a slanted line that turns flat. A kernel "either hits the flat part of the roof, which means performance is compute bound, or it hits the slanted part of the roof, which means performance is ultimately memory bound." The corner is the ridge point: "the minimum operational intensity required to achieve maximum performance." Most writers now say arithmetic intensity for the same quantity, and Apple's MPP guide uses that term.

**One worked number.** Horace He's version for an A100: "an A100 has 1.5 terabytes/second of global memory bandwidth, and can perform 19.5 teraflops/second of compute. So, if you're using 32 bit floats (i.e. 4 bytes), you can load in 400 billion numbers in the same time that the GPU can perform 20 trillion operations." The consequence: "until you're doing about a hundred operations in your unary operator, you'll be spending more time performing memory accesses than actual compute" ([Horace He](https://horace.io/brrr_intro.html)). kipply does the same arithmetic with the A100's tensor-core peak of 312 teraflops: "we get a distinct ratio here of 208 given this hardware specification. This means that if we're going to compute kv for one token, it'll take the same amount of time to compute for up to 208 tokens! Anything below, we're memory bandwidth bound" ([kipply](https://kipply.github.io/blog/transformer-inference-arithmetic/)). That 208 is the A100's ridge point for decode, and it is why batching tokens is free up to a point.

**The Apple numbers.** Apple does not publish GPU peak FLOPS in a form you can divide. Two community figures exist. metal-flash-attention's roofline table lists the M1 Max at 10,616 GFLOPS and the M4 at 3,580 ([metal-flash-attention](https://github.com/philipturner/metal-flash-attention)), without stating the precision. Apple lists the M1 Max at "up to 400GB/s of memory bandwidth" ([Apple, 2021](https://www.apple.com/newsroom/2021/10/introducing-m1-pro-and-m1-max-the-most-powerful-chips-apple-has-ever-built/)). Dividing gives a ridge point near 27 operations per byte for the M1 Max, against 208 for an A100's tensor cores. Treat the 27 as derived from two sourced numbers whose precision does not necessarily match, not as a published fact. The direction is reliable: on Apple the ridge is far to the left, so a kernel becomes compute-bound at a much lower intensity than on NVIDIA. Apple's own guide states the model for matrix multiply: "GEMMs with low arithmetic intensity are memory bound workloads, and GEMMs with high arithmetic intensity are compute bound workloads, forming the basis of a roofline model for kernel performance" ([MPP guide, section 4.1](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)).

**The third thing a kernel waits on.** Horace He splits time into "Compute: Time spent on your GPU computing actual floating point operations (FLOPS) Memory: Time spent transferring tensors within a GPU Overhead: Everything else". Overhead is the launch and the Python around it. His measurement: "Python can perform 32 million additions in one second", so "in the time that Python can perform a single FLOP, an A100 could have chewed through 9.75 million FLOPS." On a Mac through MLX, one kernel launch and its round trip measured about 195 microseconds on an M5 in the first version of this course; a 32 MB kernel's memory time at 120 GB/s is about 270 microseconds, so for small kernels the launch is most of the time. The fix is fewer launches: "if we perform x.cos().cos() , usually we need to perform 4 global reads and writes", and "with operator fusion, we only need 2 global memory reads and writes! So operator fusion will speed it up by 2x."

**One Apple-specific caution.** metal-benchmarks: "On bandwidth bound tasks, the GPU has no advantage over the CPU. Because its I/O bus width is the same (32 bytes). The 8x increase in parallelism (within the core) cannot help when the bottleneck is core I/O (outside the core)" ([metal-benchmarks](https://github.com/philipturner/metal-benchmarks)). On the slanted part of the roof, the GPU's parallelism buys nothing.

**How to use it.** Before any kernel: count the bytes it must move and the operations it must do, divide, and place it. Memory-bound means the target is percent of bandwidth and the only lever is fewer bytes. Compute-bound means the target is percent of peak and the levers are tiling and the matrix units. Launch-bound means the lever is fusion. Week 1 of the old course spent three days on this arithmetic; the pages this week apply it to each kernel family.
