# Week 2, day 2 · Elementwise, reduction, scan, online softmax

**Why this day.** These four are the primitives every larger kernel is built from. Each one teaches a rule that carries to any hardware, and the classic NVIDIA write-ups measured those rules with numbers nobody has bettered for teaching.

## The story

**Elementwise** is the trivial case: one thread per element, nothing shared. It is always memory-bound, and the only thing that can go wrong is reading memory in the wrong pattern. NVIDIA's matrix transpose post makes the pattern visible. The right metric is "effective bandwidth, calculated in GB/s by dividing twice the size in GB of the matrix (once for loading the matrix and once for storing) by time in seconds of execution". On a Tesla M2050 a plain copy reached 105.2 GB/s; a naive transpose, which reads rows and writes columns, reached 18.8; a transpose that staged a tile through shared memory so that both reads and writes were contiguous reached 51.3 ([Harris, matrix transpose](https://developer.nvidia.com/blog/efficient-matrix-transpose-cuda-cc/)). Same bytes, five times the time, from access pattern alone. The post also names the shared-memory trap: a 32 by 32 tile in which "all elements in a column of data map to the same shared memory bank, resulting in a worst-case scenario for memory bank conflicts", fixed by "making the tile 33 elements wide rather than 32".

**Reduction** is many values to one, and it teaches the target. Harris: "Reductions have very low arithmetic intensity", "1 flop per element loaded (bandwidth-optimal)", "Therefore we should strive for peak bandwidth" ([Harris, parallel reduction](https://developer.download.nvidia.com/assets/cuda/files/reduction.pdf)). His seven kernels on a 2007 G80 with an 86.4 GB/s peak went from "Kernel 1: 8.054 ms 2.083 GB/s" to "Kernel 7: 0.268 ms 62.671 GB/s", a 30.04x cumulative speedup, by fixing divergent branches, bank conflicts, addressing order, and doing more work per thread. On Apple the first three of those steps are replaced by one instruction. MLX's row reduction does "Simdgroup first", `totals[i] = op.simd_reduce(totals[i])`, which is `simd_sum` across the 32 lanes with no memory touched, then "Across simdgroups" through a small threadgroup array and one barrier ([MLX reduce_row.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/reduction/reduce_row.h)). The structure is Harris's, the first 32-wide stage is hardware.

**Scan**, the running sum, teaches data movement. A two-pass scan reads the input to reduce it, then reads it again to scan: "reduce-then-scan are typically memory-bound, but impose ~3n global data movement". NVIDIA's single-pass method "requires only ~2n data movement: n inputs are read, n outputs are written", and "the performance throughput of our parallel prefix scan approaches that of copy operations" ([Merrill and Garland](https://research.nvidia.com/sites/default/files/pubs/2016-03_Single-pass-Parallel-Prefix/nvr-2016-002.pdf)). The single-pass trick depends on blocks signalling each other through global memory. MLX's Metal scan does not do that; it loops over the axis "in blocks" inside one threadgroup, with `simd_prefix_inclusive_sum` for the 32-wide stage ([MLX scan.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/scan.h)). Whether Apple's GPUs give the forward-progress guarantee the single-pass method needs is not documented, so no one has published a look-back scan for Metal.

**Online softmax** teaches the trick that made modern attention possible. Softmax needs the maximum of a row before it can exponentiate, so the naive kernel reads the row twice, "effectively doing three memory accesses per vector element: two loads and one store". Milakov and Gimelshein showed the maximum and the normalizer can be carried together in one pass: at each step "mj ← max (mj−1 , xj) … dj ← dj−1 × e^(mj−1 − mj) + e^(xj − mj)". When a bigger maximum arrives, the running sum is rescaled by the difference. "It reduces memory accesses from 4 down to 3 per vector element", and "Softmax accelerates by up to 1.3x and Softmax+TopK combined and fused by up to 5x" ([online softmax](https://arxiv.org/abs/1805.02867)). MLX's long-row softmax kernel is this update verbatim: `prevmax = maxval;` `maxval = (maxval < vals[i]) ? vals[i] : maxval;` `normalizer *= softmax_exp(prevmax - maxval);` `normalizer += softmax_exp(vals[i] - maxval);` ([MLX softmax.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/softmax.h)). Day 4's attention kernels are this idea applied to a whole matrix.

**The rules, in one place.** Read memory so neighbouring threads touch neighbouring addresses. Measure a bandwidth-bound kernel in percent of peak, not in FLOPS. Count passes over the data; each one is a full read. Carry running state in registers so a second pass is never needed. On Apple, the 32-wide stage of any reduction or scan is one `simd_` call.

|---|---|
