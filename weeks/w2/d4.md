# Week 2, day 4 · Attention

**Why this day.** Attention is the kernel that defines a transformer's cost, and the FlashAttention idea is the single most important kernel insight of the decade. On Apple it meets a hardware limit, missing atomics, that changed the shape of the kernel.

## The story

**The problem.** Attention multiplies queries by keys to get an N by N score matrix, softmaxes each row, and multiplies by values. The naive kernel writes the score matrix to memory and reads it back: "Standard attention implementations materialize the matrices S and P to HBM, which takes O(N²) memory", and "As some or most of the operations are memory-bound (e.g., softmax), the large number of memory accesses translates to slow wall-clock time" ([FlashAttention](https://arxiv.org/abs/2205.14135)).

**The idea.** Never write the score matrix. Dao and colleagues argued that "a missing principle is making attention algorithms IO-aware -- accounting for reads and writes between levels of GPU memory", and built "an IO-aware exact attention algorithm that uses tiling to reduce the number of memory reads/writes between GPU high bandwidth memory (HBM) and GPU on-chip SRAM." The tiling works because of yesterday's online softmax: the kernel walks the keys in blocks, keeps a running maximum and normalizer per query row in registers, and rescales as it goes, so the softmax never needs the whole row at once. The paper's theorem: standard attention needs on the order of N·d + N² memory accesses, FlashAttention on the order of N²d²/M where M is the on-chip memory size, and "For typical values of d (64-128) and M (around 100KB), d² is many times smaller than M", giving "up to 9× fewer" accesses. Measured: "3× speedup on GPT-2 (seq. length 1K)".

**The second version, and the lesson in it.** A year later the same author wrote that "FlashAttention is still not nearly as fast as optimized matrix-multiply (GEMM) operations, reaching only 25-40% of the theoretical maximum FLOPs/s", and that "the inefficiency is due to suboptimal work partitioning between different thread blocks and warps on the GPU, causing either low-occupancy or unnecessary shared memory reads/writes" ([FlashAttention-2](https://arxiv.org/abs/2307.08691)). The fixes were about who does what, not about the algorithm: fewer non-matmul operations, parallelism across thread blocks even within one head, and splitting work between warps "to reduce communication through shared memory". Result: "around 2× speedup compared to FlashAttention, reaching 50-73% of the theoretical maximum FLOPs/s on A100". The same algorithm, half the time, from partitioning alone. Week 6 follows versions 3 and 4 onto newer hardware.

**Attention on Apple.** Philip Turner ported the idea to Metal and met a wall: "Apple hardware lacks native FP32 atomics (`metal::atomic<float>` is emulated)". The official backward pass uses atomics to accumulate gradients; his "alternative backward pass was designed with higher compute cost (7 GEMMs instead of 5 GEMMs)", and "uses less memory than Dao-AILab/flash-attention" because it needs no scratch space for them ([metal-flash-attention](https://github.com/philipturner/metal-flash-attention)). He also hit the register wall from week 1: "At large head dimensions (e.g. 256), none of the matrix blocks can fit into registers. Not even the accumulator can." His results, as a fraction of his roofline: forward 85 to 86 percent on the M1 family, 82 to 94 percent on M3; forward plus backward 62 to 64 percent on M1 and 61 to 71 on M3. His NVIDIA comparisons use a different construction and are his own, so read the Apple column, not the cross-vendor one.

**Prefill and decode are two kernels.** MLX's fused attention switches on the number of query tokens: `if (query_sequence_length > 8)` it runs the full tiled kernel, otherwise a vector kernel, `sdpa_vector`, for decode, where one query attends to a long cache ([MLX scaled_dot_product_attention.cpp](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/scaled_dot_product_attention.cpp)). The vector path "requires the query length times the GQA factor to be at most 32" and has a two-pass variant that splits the key axis across threadgroups, `blocks = 64` rising to 1,024 as the cache grows. Prefill is a matmul and compute-bound; decode is a matvec over the cache and memory-bound. The serving course taught why; this is where it lives in code.

**A date to know.** Until 2026-09-29, MLX's attention had no fused backward on Metal; training fell back to the unfused path. Commit 83b976ea, "Adding VJP for the scaled dot product attention. (#4563)", added one, and the forward now emits the log-sum-exp only when that backward exists: `output_logsumexp = is_training && has_fast_vjp`. The remaining gap is attention sinks and array masks. Week 4 returns to this as a capstone candidate, with a warning: it moved while this course was being written.

|---|---|
