# Week 2, day 3 · Matrix multiply

**Why this day.** Matrix multiply is the one kernel where compute can win over memory, and it is the kernel where Apple's advice differs most from NVIDIA's. The ladder of optimizations is universal; which rungs matter on an Apple core is not.

## The story

**Why matmul is different.** A matrix product with sides M, N, K does M·N·K multiply-adds while reading M·K + N·K inputs and writing M·N outputs. Apple's guide gives the intensity: "(M * N * K) / ((M * K) + (N * K)) == (M * N) / (M + N) ops per input element", and "you can make the number of compute operations per load arbitrarily large by increasing both M and N, achieving the best-case scenario when M == N" ([MPP guide, section 4.1](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)). Big square matrices are compute-bound on any GPU. The catch, in the same section: "this type of roofline model assumes perfect input reuse in the kernel implementation where each input element loads from device memory only once, and all other accesses hit in the cache. In reality, achieving good cache hit rates requires a carefully tiled implementation". The whole craft is reuse.

**The universal ladder.** Simon Boehm's worklog on an NVIDIA A6000 is the clearest record of what each step buys. Ten kernels, FP32, 4092 by 4092, as a percent of NVIDIA's cuBLAS library ([siboehm](https://siboehm.com/articles/22/CUDA-MMM)):

| Kernel | GFLOPS | Percent of cuBLAS |
|---|---|---|
| 1 Naive | 309 | 1.3% |
| 2 Global memory coalescing | 1,987 | 8.5% |
| 3 Shared memory caching | 2,980 | 12.8% |
| 4 1D block tiling | 8,475 | 36.5% |
| 5 2D block tiling | 15,972 | 68.7% |
| 6 Vectorized memory access | 18,237 | 78.4% |
| 9 Autotuning | 19,721 | 84.8% |
| 10 Warp tiling | 21,779 | 93.7% |
| cuBLAS | 23,250 | 100% |

Read the jumps. Coalescing alone, which is yesterday's access-pattern rule, is 1.3 to 8.5 percent. The two tiling steps, where each thread computes a small block of outputs and reuses what it loaded, take 12.8 to 68.7. His rule for when to stop: "We'll continue optimizing arithmetic intensity for as long as we're still memory bound." His cost: "two weekends to write the first 6 kernels which reach 80% of peak FLOPs, and then 4 more weekends to do autotuning and warptiling to get to 94%." And one sentence that explains why reading other people's matmul kernels is hard: "cuBLAS contains not one single implementation of SGEMM, but hundreds of them."

Volkov and Demmel found the same thing in 2008 on an earlier GPU and drew a conclusion that still holds: "The code performed at 32%, 49%, 58% and 59% of the peak when running 1, 2, 3 and 4 threads per core", where "4 threads per GTX280 core correspond to 25% occupancy. This indicates that one should not over-optimize for the occupancy" ([Volkov SC08](https://mc.stanford.edu/cgi-bin/images/6/65/SC08_Volkov_GPU.pdf)). The best matmuls keep their data in registers and run few threads; occupancy is not the goal, reuse is.

**Apple's version of the ladder.** MLX's steel library does the same tiling with the 8 by 8 simdgroup matrices from week 1: `simdgroup_multiply_accumulate(D, A, B, C)` on `simdgroup_matrix<T, 8, 8>` tiles, with a threadgroup tile of BM by BN split into WM by WN simdgroup tiles, `TM = BM / (kFragSize * WM)` ([MLX steel mma.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/steel/gemm/mma.h)). Its loader stages tiles through threadgroup memory: "Load from device memory into threadgroup memory - without bound checking" ([loader.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/steel/gemm/loader.h)). That is Boehm's rung 3.

Then Apple's 2026 guide says rung 3 is unnecessary on an M5: "Theadgroup [sic] memory staging isn't necessary for the most optimized GEMM kernels. The on-chip memory hierarchy works best when you directly access device memory and allow the different levels of caching to work as designed." And the software pipelining that the NVIDIA worklogs in week 5 spend most of their time on: "Kernels don't require any explicit software pipelining to overlap memory and compute operations. Metal achieves this execution overlap naturally with sufficient thread occupancy on each core." Apple's conclusion: "In combination, these properties lead to optimal code that's much simpler than existing platforms." The guide gives starting tiles for the M5: "a 2 x 2 tile of simdgroups per threadgroup", a simdgroup tile of "SM == SN == 32" for 16-bit operands, and "BK == 128". It adds two warnings that are the Apple-specific ladder: "Beyond a certain threshold, increasing simdgroup tile size may reduce performance if operands are too large to fit in fast thread-local memory", and "Each barrier reduces the pool of instructions available to execute". It also asks for Morton ordering of threadgroups so that "different cores maximally reuse shards of both input matrices".

Both documents are Apple's. MLX steel stages through threadgroup memory; the MPP guide, written for the M5 with its dynamic caches, says not to. There is no published benchmark of one against the other. For you the lesson is a question to ask of any kernel an AI proposes: on this chip, does the staging rung pay, or does it just add barriers?

**One measured Apple number.** metal-flash-attention, an attention kernel built from these same simdgroup matrices, reached "a consistent 4400 gigainstructions per second on M1 Max (83% ALU utilization)" ([metal-flash-attention](https://github.com/philipturner/metal-flash-attention)). That is the kind of figure a well-tiled Apple kernel can hit, and the author measures in instructions, not FLOPS, because on Apple "it maps more directly to the algorithm."
