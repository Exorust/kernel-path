# Week 3, day 1 · llama.cpp's Metal backend

**Why this day.** The first fast large-language-model runs on Apple GPUs came from one pull request in June 2023. The story explains why Apple silicon is good at this at all, and the table it produced is still the best public measurement of how token speed follows bandwidth across M-series chips.

## The story

In April 2023 Georgi Gerganov opened a discussion on adding GPU support to his tensor library, with a side note that "Another tool, for example `ggml-mps`, can do similar stuff but for Metal Performance Shaders" ([discussion #915](https://github.com/ggml-org/llama.cpp/discussions/915)). Seven weeks later he merged pull request #1642, "llama : Metal inference": "Add full GPU inference of LLaMA on Apple Silicon using Metal" ([PR #1642](https://github.com/ggml-org/llama.cpp/pull/1642), merged 2023-06-04).

Three sentences in that pull request explain the design, and all three are week 1 and week 2 in action. "This PR implements support only for `Q4_0`, but all other quantizations can easily be added in the future": the first thing worth having on the GPU was the quantized weight format. "The implemented shaders currently focus on `qMatrix` x `Vector` multiplication which is normally needed for LLM text-generation. For other tasks that involve `Matrix` x `Matrix` (for example prompt ingestion, perplexity computation, etc) we don't have an efficient implementation yet, so we fallback to the CPU / ANE": decode is a matvec, prefill is a matmul, and the matvec came first. And "Works well with `mmap` to avoid model data duplication in memory": the weights were mapped from disk into the one memory pool, and the GPU read them there. No copy, because of unified memory. The first logged speed was "48.88 ms per token" for a 7-billion-parameter model, on a machine the log does not name.

Five days later a second contributor tuned the one kernel that mattered. Pull request #1775, "metal : faster q40", in full: "For a run with 256 tokens prediction time is now 23 ms / token on my 30-core M2 Mac GPU, down from 27 ms/token. Avoiding a local copies to `float4` and `uchar4` brings ~8% speedup, using 64 threads per thread group in an 8x8 arrangement brings another 9%. Memory throughput is now ~270 GB/s, so ~90% of theoretical limit" ([PR #1775](https://github.com/ggml-org/llama.cpp/pull/1775)). That is the roofline from week 2 day 1 as a progress report: the kernel is measured in percent of bandwidth, two small changes to how threads are arranged gave 17 percent, and the author stopped at 90 percent of the roof because there was nothing left.

**The table.** In November 2023 Gerganov opened a discussion that is still updated, "Performance of llama.cpp on Apple Silicon M-series" ([discussion #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)). It reports a 7-billion-parameter model on every chip people own, with prompt processing (PP, tokens per second for prefill) and text generation (TG, tokens per second for decode) against the chip's bandwidth and core count. Selected rows for the 4-bit format:

| Chip | Bandwidth GB/s | GPU cores | PP tok/s | TG tok/s |
|---|---|---|---|---|
| M1 Pro | 200 | 16 | 266 | 36.4 |
| M2 Ultra | 800 | 76 | 1,238 | 94.3 |
| M4 Max | 546 | 40 | 886 | 83.1 |
| M5 Max | 614 | 40 | 3,220 | 119.9 |
| M5 Ultra | 1,228 | 80 | 4,945 | 179.1 |

The discussion's own plot script says what to look at: "PP vs GPU Cores and TG vs Bandwidth". Decode follows bandwidth: 200 GB/s gives 36 tokens per second, 1,228 gives 179. Prefill follows cores, until the M5. The M4 Max and M5 Max have the same 40 cores and bandwidth 12 percent apart, yet prefill goes from 886 to 3,220 tokens per second, 3.6 times. That is the neural accelerator in every M5 core, and tomorrow is about it. One caution from the data itself: the M4 and M5 rows were measured on different commits, so the comparison mixes software versions.

**What it became.** The 2023 backend was a single file of Metal shaders. On 2026-10-08 the Metal kernels directory held 40 files, and the largest by far was still the matvec: `mul_mv.metal` at 133,101 bytes, against `mul_mm.metal` at 56,349. Beside them sit a flash-attention family, `gated_delta_net.metal` for the linear-attention models of day 3, and on the host side a fusion pass and a tuning table, `ggml-metal-fusion.cpp` and `ggml-metal-tuning.cpp`. In November 2025 the backend began using Metal 4's tensor API: "Rework matrix-matrix multiplication / Use Tensor API when available" ([PR #16634](https://github.com/ggml-org/llama.cpp/pull/16634)). Three years on, the biggest file is still the kernel the first pull request was built around.
