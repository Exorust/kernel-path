# Week 3, day 5 · Launch overhead at scale

**Why this day.** The last three days were about kernels. This one is about the gaps between them. On small models at batch one, the gaps cost more than the kernels, and on Apple the gap has a specific name: the command buffer.

## The story

**The arithmetic.** Hazy Research set the frame in May 2025: "for single-sequence generation in 16-bit precision on a single H100, the memory limit is 3.35TB/s / 2.48GB = ~1350 forward passes per second. But with 7 kernel launches per layer, and 16 layers, even with an optimistic 5 us of stalling per kernel (counting stragglers, kernel launch, and memory latencies), generation would run at just ~770 forward passes per second" ([Hazy Research, No Bubbles](https://hazyresearch.stanford.edu/blog/2025-05-27-no-bubbles)). A small model does so little work per kernel that "around a hundred separate kernels" per forward pass, each with a few microseconds of nothing before and after it, cap throughput at little more than half the bandwidth limit. Their fix was one persistent kernel for the whole model: "on an H100, we use 78% of memory bandwidth and outperform existing systems by over 1.5x." They also measured the thing itself: "running on a CUDA stream incurs a launch cost of about 2.1 microseconds, and with CUDA graphs the launch cost only decreases to around 1.3 microseconds".

A later reconstruction split their kernel back into 81 kernels joined by CUDA graphs and dependent launch and reached 97.4 percent of the megakernel's throughput (week 6 day 2 has the source). The schedule mattered; the single kernel was packaging. Keep that: the enemy is idle time between dispatches, not the count of dispatches.

**The same tax on Apple, where it lives.** In MLX the unit of submission is the Metal command buffer from week 1 day 3. An unmerged pull request from September 2026 measured what the defaults do to a large mixture-of-experts model: "MLX commits a command buffer after `max_ops_per_buffer` operations or `max_mb_per_buffer` MB of distinct inputs: 50 / 50 on M3 Ultra ... Weights count toward the MB budget. A batch-1 decode step of a large mixture-of-experts model therefore commits after nearly every expert matmul, while `eval` lets at most 10 command buffers be in flight" ([MLX PR #4562](https://github.com/ml-explore/mlx/pull/4562)). Instruments showed "~231 command buffers per decode token, each covering ~0.25 ms of GPU work, so the in-flight window is only ~2.5 ms of lookahead; the GPU busy only 68% of the time at 123k context." A third of the GPU's time was the gap. Raising the limits for decode gave "15.4 → 18.1 (+17.5%)" tokens per second at 123k context, "GPU busy 83 → 89%, and command buffers per 4 s fell from 24,107 to 2,925". The same change applied to prefill would have cost memory: "A 30k-token prefill then held +88 GB instead of +8 GB", so the setter is scoped. The measurement is on two M3 Ultra machines running tensor-parallel, and the pull request is not merged, so treat it as a measured diagnosis rather than shipped behaviour.

**llama.cpp's arc, three years long.** In June 2023 Gerganov tried the obvious thing: "Use multiple command buffers - Enqueue them at start - Encode the commands in parallel on separate threads ... On M1 Pro there is no difference in the measured inference time" ([PR #1860](https://github.com/ggml-org/llama.cpp/pull/1860)). Encoding was not the bottleneck. In September 2025 he attacked the dependencies instead: "keep track of the memory intervals/ranges from which we read data and to which we write data. Using this information, for the new node we can determine if it can safely run concurrently with all the concurrent ops prior to it", with "The benefits are large for TG and decent for PP": a 270-million-parameter model went from 333.98 to 392.28 tokens per second, 1.17x, and a 20-billion-parameter MoE from 120.91 to 133.14, 1.10x ([PR #15929](https://github.com/ggml-org/llama.cpp/pull/15929)). Letting independent kernels overlap filled the gaps that parallel encoding could not. The smaller the model, the bigger the gain, which is Hazy's arithmetic again.

**The entry-level version.** MLX's own documentation shows the simplest form of the fix. A gelu written as a chain of elementwise operations is "overhead bound" on small arrays, and "all of the operations in the gelu are fusible into a single kernel with compile()": "On an M1 Max the times are 15.5 and 3.1 milliseconds. The compiled gelu is five times faster" ([MLX compile docs](https://ml-explore.github.io/mlx/build/html/usage/compile.html)). Five launches became one.

**Three authors, one caveat.** The kda-metal kernel from day 3 says its 2x "needs batched command encoding around it". The pMLX author from day 4 blames the shared decode loop for "fixed overhead the runtimes themselves can't remove". The MLX pull request above measured that overhead at a third of GPU time. Three people who did not coordinate wrote the same sentence: a fast kernel inside a leaky schedule is a fast kernel that does not show up in tokens per second. For a director, the question to ask before any kernel work is whether the step is kernel-bound or gap-bound, and the Instruments timeline from week 4 day 2 is how to see it.
