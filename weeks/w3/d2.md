# Week 3, day 2 · MLX steel and the M5 neural accelerators

**Why this day.** The M5 changed the roofline. Compute went up four times and bandwidth thirty percent, so matrix multiplies that were memory-bound became compute-bound, and the kernels had to change shape. One pull request shows what that looked like, with its own numbers.

## The story

Apple's words for the M5: "a next-generation 10-core GPU architecture with a Neural Accelerator in each core, enabling GPU-based AI workloads to run dramatically faster, with over 4x the peak GPU compute performance compared to M4", with "a nearly 30 percent increase in unified memory bandwidth to 153GB/s", and the door for programmers: "directly programming the Neural Accelerators using Tensor APIs in Metal 4" ([Apple, October 2025](https://www.apple.com/newsroom/2025/10/apple-unleashes-m5-the-next-big-leap-in-ai-performance-for-apple-silicon/)). MLX calls these paths NAX. On 2026-10-08 its kernel tree held a `nax.h` for matrix multiply and another for attention, five NAX GEMM variants (fused, gather, segmented, split-K, thin), `quantized_nax.h` at 49,101 bytes, and NAX kernels for the linear-attention update of tomorrow, including its backward pass.

**Why four times the compute changes the kernel.** The roofline arithmetic from week 2: a matrix multiply's intensity is (M·N)/(M+N) operations per input element, and "you can make the number of compute operations per load arbitrarily large by increasing both M and N" ([MPP guide, section 4.1](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)). On the M4 a large matmul was near the memory roof. Lift the compute roof four times with the bandwidth almost unchanged and the ridge point moves right: the same matmul is now compute-bound, and the kernel's job becomes keeping the accelerators fed. Yesterday's llama.cpp table showed the result from the outside, prefill going from 886 to 3,220 tokens per second on the same 40 cores.

**The case: split-K.** In January 2026 a contributor found that the new NAX matrix kernels had a weak shape. Pull request #3018, "Add NAX Split-K GEMM for large-K matmuls to improve performance": "Adds NAX Split-K GEMM support to address high runtime variance and slow tail cases in large-K matmals on M5 GPU. For GEMMs with very large K dimensions, partitioning work along K substantially reduces variance and eliminates slow tail cases, achieving up to ~1.6× speedup over the fused NAX GEMM" ([PR #3018](https://github.com/ml-explore/mlx/pull/3018), merged 2026-01-26).

The mechanism is a week 1 fact. When K, the inner dimension, is very large and the output is moderate, there are few output tiles, so few threadgroups, so the ten cores are not full. "New kernel `steel_gemm_splitk_nax` partitions K-dimension work across threadgroups, then accumulates partial sums": cut the long inner loop into pieces, give each piece to its own threadgroup, add the pieces at the end. More threadgroups, full cores, at the cost of one extra reduction. The numbers, bfloat16 on an M5:

| M | N | K | Before | After | Speedup |
|---|---|---|---|---|---|
| 2048 | 2048 | 10240 | 156.11 ms | 142.52 ms | 1.10x |
| 4096 | 6144 | 21504 | 2807.22 ms | 1734.34 ms | 1.62x |
| 6144 | 6144 | 21504 | 4078.63 ms | 2635.42 ms | 1.55x |

The gain grows with K relative to M and N, which is the prediction the mechanism makes. In fp32 the small shape lost slightly, 0.98x, so the kernel is only used when a rule says so: "Dispatch heuristic: batch_size==1 AND M×N >= 2048^2 AND K >= 10240 AND K >= 3×max(M,N) AND NAX available". And the author is plain about how the thresholds were found: "empirically determined on M5 GPU".

**The brittleness.** A kernel tuned by measurement on one chip has edges. In August a second contributor measured one: an unmerged pull request found a "dispatch cliff" between M=32 and M=33 on an M5 Max, where the M=33 to M=32 ratio "moved from 0.781/0.733/0.732/0.682 on the baseline to 1.005/1.002/1.000/1.007 on the candidate", with "1.22–1.49x" gains across 33 affected shapes and no change on the controls ([PR #4237](https://github.com/ml-explore/mlx/pull/4237), closed, not merged). A one-row change in batch size dropped speed by a third because a threshold routed it to a different kernel. Dispatch rules are code too, and they have bugs.

**The guide that followed.** Two months after split-K merged, Apple published the MPP guide with the M5 starting points from week 2 day 3: a 2 by 2 tile of simdgroups, 32 by 32 per simdgroup, BK of 128, Morton ordering, no threadgroup staging. The guide and the pull request are the same lesson from two sides: on the M5 the matmul is compute-bound, the accelerators are the roof, and the kernel's shape is set by keeping every core busy without spilling registers.

**For the director.** When an AI proposes a matmul kernel for an M5, ask three things this page gives you: which roof the shape hits, whether the number of threadgroups fills ten cores, and what rule decides when the kernel is used. The 1.62x came from the second question; the cliff came from the third.

## Numbers to remember

| | |
|---|---|
| M5 | over 4x GPU compute, about 1.3x bandwidth, against M4 |
| Split-K | up to 1.62x at K=21504; 1.10x at K=10240; fp32 0.98x |
| Dispatch rule | M×N ≥ 2048², K ≥ 10240, K ≥ 3·max(M,N) |
| Cliff | M=32 to 33, ratio 0.68 to 1.00 after the fix, unmerged |
