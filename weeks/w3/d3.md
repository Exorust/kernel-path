# Week 3, day 3 · Linear attention on MLX

**Why this day.** The newest model families replace most attention layers with a linear-attention update that runs as a loop over tokens. Three attempts to make it fast on Apple silicon in 2026 give three different lessons: one about baselines, one about where state lives, and one about what a 2x kernel is worth end to end.

## The story

**The layer.** Qwen3-Next runs "12 * (3 * (Gated DeltaNet -> MoE) -> 1 * (Gated Attention -> MoE))", Qwen3.5 "8 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))", and Kimi Linear "a 3:1 KDA-to-global MLA ratio" ([model cards](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct)). Three of every four layers are a gated delta rule: a small state matrix per head that is decayed, corrected, and read once per token. There is no key-value cache, which is why these models fit long contexts on a laptop, and the update is sequential in the token, which is why prefill is slow. In mlx-lm the kernel is in `gated_delta.py`: a loop `for (int t = 0; t < T; ++t)` with two `simd_sum` calls per token ([gated_delta.py](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/models/gated_delta.py)).

**Attempt one: the wrong baseline.** In May 2026 a contributor ported the chunked algorithm used on NVIDIA, which turns the token loop into blocks of dense matrix multiplies, and reported it against the Python per-token loop: 1.5x at 512 tokens, 6.8x at 2,048, "56×" at 16,384 ([mlx-lm PR #1241](https://github.com/ml-explore/mlx-lm/pull/1241)). The author closed the pull request the same day: "the existing gated_delta_kernel already handles prefill in a single Metal dispatch with recurrent state in thread registers, which is faster on Apple Silicon than the chunked FlashQLA algorithm (which is optimized for CUDA/Triton). Benchmarks show the existing implementation outperforms this approach for T ≥ 1024." The 56x was real and irrelevant: it was measured against a loop nobody shipped. The Metal kernel that keeps its state in registers and never leaves the GPU beat the algorithm that wins on NVIDIA. This is the first lesson of the week: a speedup is only as good as its baseline, and the right baseline on Apple is the fused kernel that already exists.

**Attempt two: where the state lives.** In July a different contributor looked at the existing kernel and found the real limit: "The existing gated-delta prefill kernel assigns one full 32-lane SIMD-group to each value row. With `Dk == 128`, each lane owns only four state elements, while every timestep still performs two full-SIMD reductions per row", which "makes the kernel latency-bound on the target Qwen3.5/3.6 shapes" ([mlx-lm PR #1559](https://github.com/ml-explore/mlx-lm/pull/1559), merged 2026-08-27). Thirty-two lanes each holding four numbers and synchronizing twice per token is a kernel that waits on its own reductions. The fix repacked the work: "four lanes cooperate on each value row; each lane retains 32 contiguous state elements in registers". Fewer lanes per row, more state per lane, fewer cross-lane reductions. Measured on an M5 Max at the Qwen3.6 shape: "Per gated-delta layer | 2.54-2.56 ms | 1.34-1.38 ms | approximately 1.8-2.0x". The kernel is twice as fast.

Then the row underneath: "End-to-end prefill | baseline | optimized | 1.064x / +6.4%". A 2x kernel gave 6 percent, because the gated-delta layers were a small share of prefill time once the kernel was fast. That is the second lesson, the one every kernel director has to carry: the kernel's share of the whole is the ceiling on what the kernel can give.

The pull request also did something that week 4 will call the right way to ship: "the packed kernel is bitwise-identical by construction to an explicit-tree comparator kernel that the tests pin it against", with a kill switch, `MLX_GDN_PACKED=0`, that routes back to the old kernel. Correctness was a contract written into the code, not a tolerance.

**Attempt three, independent.** In August a standalone repository applied the same idea to Kimi's variant of the rule, KDA, where "Kimi K3 swaps softmax attention for a gated delta rule in 69 of its 93 layers". It wrote the obvious kernel and then "a register-resident rewrite that runs about 2x faster. Both are bit-exact across runs": at the real shape, "88.02 us" to "44.00 us", 2.00x, on an M5, where "roughly 1,150 memory instructions become about 19 vector operations" per lane ([kda-metal](https://github.com/Exorust/kda-metal)). Two codebases that had never seen each other, one conclusion: on an Apple core, with its large register file from week 1, the win is to keep the state in registers and touch memory once per token. The repository is this course author's; it is cited for its measured table and for the caveat it states itself: "this measures kernel GPU time in isolation; inside a full engine the win also needs batched command encoding around it", which is day 5.

**What is still open.** The chunked formulation that failed in May is not dead; it is what the NVIDIA libraries use and what week 6 covers. As of 2026-10-08, mlx-lm has an open pull request for a chunkwise version for training, and an issue asking for "a chunked (WY / parallel) formulation like the one in flash-linear-attention". MLX core gained NAX kernels for the update and its backward in September. The Metal prefill kernel that beats the register-resident scan at long context has not been published. Week 4 day 5 offers it as a capstone.
