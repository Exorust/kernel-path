# Week 6, day 1 · FlashAttention 1 to 4

**Why this day.** One kernel, four versions, four GPU generations, and the authors' own numbers for each. It is the clearest record anywhere of how a kernel follows the hardware, and every version's lesson applies to the Apple attention kernels from week 2 day 4.

## The story

**Version 1, 2022: stop writing the score matrix.** "We propose FlashAttention, an IO-aware exact attention algorithm that uses tiling to reduce the number of memory reads/writes between GPU high bandwidth memory (HBM) and GPU on-chip SRAM." Results: "15% end-to-end wall-clock speedup on BERT-large (seq. length 512) compared to the MLPerf 1.1 training speed record, 3× speedup on GPT-2 (seq. length 1K), and 2.4× speedup on long-range arena (seq. length 1K-4K)" ([FlashAttention](https://arxiv.org/abs/2205.14135)). The mechanism was week 2 day 2's online softmax applied blockwise. The problem it attacked was bytes.

**Version 2, 2023: give the work to the right threads.** "FlashAttention is still not nearly as fast as optimized matrix-multiply (GEMM) operations, reaching only 25-40% of the theoretical maximum FLOPs/s", because of "suboptimal work partitioning between different thread blocks and warps on the GPU, causing either low-occupancy or unnecessary shared memory reads/writes" ([FlashAttention-2](https://arxiv.org/abs/2307.08691)). Three changes, none to the algorithm: "(1) tweak the algorithm to reduce the number of non-matmul FLOPs (2) parallelize the attention computation, even for a single head, across different thread blocks to increase occupancy, and (3) within each thread block, distribute the work between warps to reduce communication through shared memory." Result: "around 2× speedup compared to FlashAttention, reaching 50-73% of the theoretical maximum FLOPs/s on A100", and "up to 225 TFLOPs/s per A100 GPU (72% model FLOPs utilization)". The problem it attacked was partitioning.

**Version 3, 2024: use the new hardware.** On the next chip the old kernel fell back: "FlashAttention-2 achieving only 35% utilization on the H100 GPU" ([FlashAttention-3](https://arxiv.org/abs/2407.08608)). The fix used week 5 day 4's units: "exploiting asynchrony of the Tensor Cores and TMA to (1) overlap overall computation and data movement via warp-specialization and (2) interleave block-wise matmul and softmax operations, and (3) block quantization and incoherent processing that leverages hardware support for FP8 low-precision." Some warps move data while others compute; the matmul of one block runs while the softmax of the previous one finishes. Result: "speedup on H100 GPUs by 1.5-2.0× with FP16 reaching up to 740 TFLOPs/s (75% utilization), and with FP8 reaching close to 1.2 PFLOPs/s", with the FP8 path achieving "2.6× lower numerical error than a baseline FP8 attention". The problem it attacked was asynchrony.

**Version 4, 2026: the matmul is no longer the bottleneck.** On Blackwell "tensor core throughput doubles while other functional units (shared memory bandwidth, exponential units) scale more slowly or remain unchanged" ([FlashAttention-4](https://proceedings.mlsys.org/paper_files/paper/2026/file/ae8b0b5838ba510daff1198474e7b984-Paper-Conference.pdf)). The exponentials in the softmax, which were free beside the matmul for three generations, became the limit. The fixes: "(1) redesigned pipelines that exploit fully asynchronous MMA operations and larger tile sizes, (2) software-emulated exponential and conditional softmax rescaling that reduces non-matmul operations, and (3) leveraging tensor memory and the 2-CTA MMA mode to reduce shared memory traffic and atomic adds in the backward pass." Computing some exponentials with ordinary arithmetic instead of the special unit, and skipping the rescale when the maximum has not changed. Result: "up to 1.3× speedup over cuDNN 9.13 and 2.7× over Triton on B200 GPUs with BF16, reaching up to 1613 TFLOPs/s (71% utilization)", written "entirely in CuTe-DSL embedded in Python, achieving 20-30× faster compile times compared to traditional C++ template-based approaches". The problem it attacked was the unit next to the matmul.

**The table.**

| Version | Chip | Attacked | Result | Of peak |
|---|---|---|---|---|
| 1 | A100 | bytes | 3x on GPT-2 | 25 to 40% |
| 2 | A100 | partitioning | 2x over v1, 225 TFLOPS | 50 to 73% |
| 3 | H100 | asynchrony | 1.5 to 2x, 740 TFLOPS | 75% |
| 4 | B200 | exponentials, shared memory | 1.3x over cuDNN, 1,613 TFLOPS | 71% |

Version 4's 71 percent is lower than version 3's 75 even though the kernel is twice as fast, because the peak doubled and the rest of the chip did not. The percentage is honest about the hardware; the TFLOPS figure is honest about the kernel.

**What it means on your Mac.** Each version's problem exists on Apple with a different answer. Bytes: week 2 day 4's Metal flash attention did the same tiling and hit a different wall, missing atomics. Partitioning: week 3 day 3's packed kernel was version 2's lesson, who holds what, on a linear-attention scan. Asynchrony: Apple's guide says the hardware overlaps for you, so there is no warp specialization to write. The exponential problem: the M5's neural accelerators raised matrix throughput four times; whether the M5's softmax is now the attention bound on Apple is an open question nobody has published, and it is exactly the kind of measurement week 4's loop is for.
