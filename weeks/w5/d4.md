# Week 5, day 4 · Hopper: TMA, wgmma, the H100 worklog

**Why this day.** Yesterday's ladder reaches 4 percent on an H100. Today is the new ladder: two hardware units that have no Apple equivalent, read through the worklog of a person who climbed from 4 percent to 107 percent of NVIDIA's own library in a single file.

## The story

**Two new units.** The first moves data. "TMA (Tensor Memory Accelerator) is a new feature introduced in the NVIDIA Hopper architecture for doing asynchronous memory copy between a GPU's global memory (GMEM) and the shared memory (SMEM) of its threadblocks (i.e., CTAs)", and "for a TMA copy, only one thread will be responsible for issuing the TMA operation" ([Colfax, TMA](https://research.colfax-intl.com/tutorial-hopper-tma/)). One thread asks for a whole tile; the hardware moves it while the other threads compute. The second does the math. "Hopper introduces the asynchronous warpgroup-level matrix multiply and accumulate operation (WGMMA)", where "A warpgroup consists of four contiguous warps, i.e., 128 contiguous threads", and "A notable requirement of WGMMA is that operand B must always be stored in shared memory (SMEM). In contrast, operand A can be located in either SMEM or register memory (RMEM), and the accumulator C is always held in RMEM" ([Colfax, wgmma](https://research.colfax-intl.com/cutlass-tutorial-wgmma-hopper/)). Four warps issue one matrix multiply together, asynchronously, from shared memory. Both units are why week 5 day 1's 228 KB of shared memory exists: it is where TMA lands tiles and where wgmma reads them.

**The climb.** Shankhdhar's worklog on an H100 in BF16, with cuBLAS at 716 TFLOPS as the target ([Shankhdhar](https://cudaforfun.substack.com/p/outperforming-cublas-on-h100-a-worklog)):

| Step | TFLOPS | What changed |
|---|---|---|
| Boehm's final kernel, adapted | 32 | the old ladder |
| Tensor cores, TMA, barriers | 317 | "a big jump over 32 TFLOPS of previous kernel" |
| wgmma m64n128k16 | 423 | the asynchronous matrix instruction |
| 128 by 128 tiles, queue depth 5 | 498 | bigger tiles, deeper pipeline |
| larger tile | 610 | |
| 128 by 256 tile | 123 | "insufficient register resources" |
| back, plus tuning | 631 | |
| L2-aware scheduling | 660 | "L2 cache hit rate of 83%, meanwhile cuBLAS only hits 70%" |
| | 704 | "98% performance of cuBLAS" |
| | 734 | "102% of cuBLAS performance" |
| final | 764 | "107% of cuBLAS performance" |

His sentence on the first jump: "This is not true for H100, where tensor cores are mandatory for high throughput." His sentence on the documentation: "Unfortunately, there's no documentation of these instructions in CUDA C++ guide and we have to look at PTX guide." And the final claim, scoped: "The final kernel outperforms cuBLAS by 7% for N=4096. It fits in a single C++ file without any dependencies", with "2% faster for N=512", "17% faster for N=1024", "7-8% faster for N=2048,4096", "1.5% faster for N=8192".

**The regression that teaches the most.** One row in that table goes down by five times. Doubling the tile to 128 by 256 produced "123 TFLOPs" and a compiler warning, "insufficient register resources", because "Output tile uses 128 x 256 = 32768 registers in the thread block". The accumulator must live in registers, and the register file per SM from day 1 is 65,536. Half of it for one tile's output left nothing for the rest, and the kernel spilled. This is week 1 day 2's register cliff and week 2 day 3's MPP warning, "increasing simdgroup tile size may reduce performance if operands are too large to fit in fast thread-local memory", on different hardware with the same shape. The fix was a smaller tile and a deeper pipeline, not a bigger one.

**The production version.** DeepSeek's DeepGEMM is the same design, shipped: "Despite its lightweight design, DeepGEMM's performance matches or exceeds expert-tuned libraries across various matrix shapes", with "up to 1550 TFLOPS on H800" in FP8, and a stated relationship to the libraries: "DeepGEMM leverages some concepts from CUTLASS and CuTe, but avoids heavy reliance on their templates or algebras" ([DeepGEMM](https://github.com/deepseek-ai/DeepGEMM)). A small, readable Hopper matmul that beats the vendor is possible, and two independent authors did it.

**Beware the Gordic line.** Gordic's post summarizes both worklogs and reports Shankhdhar "hitting ~107% of cuBLAS performance on a few target matrix dimensions" ([Gordic](https://www.aleksagordic.com/blog/matmul)). It is a summary, not a third measurement; the 107 percent rests on one person's benchmark on one card at four sizes, and it is "a few target matrix dimensions" by his own phrasing. Treat the 98 to 107 percent band as the finding, and the exact figure as one run.

**Against Apple.** There is no TMA on an M5: the MPP guide's statement that "Kernels don't require any explicit software pipelining" is Apple saying the hardware does the overlap that TMA plus barriers do by hand on Hopper. There is no warpgroup; the simdgroup is the unit, and the neural accelerator is reached through tensor ops inside one. The shape of the best kernel differs because the memory inside the core differs, which was week 5 day 1's point. What transfers is the regression: on both platforms, the first tile size that spills registers is the ceiling.
