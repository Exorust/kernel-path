# Week 5, day 2 · CUDA, PTX, SASS, Triton, CUTLASS

**Why this day.** On Apple there is one language and one compiler you never see. On NVIDIA there are four layers, and the kernels that made news are written at different ones. Knowing which layer a kernel lives at tells you what an AI can change and what it cannot.

## The story

**The layers.** A CUDA kernel is C++ run on the GPU: "functions which execute on the GPU which can be invoked from the host are called kernels. Kernels are written to be run by many parallel threads simultaneously" ([CUDA C++ basics](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html)). The compiler, nvcc, "splits CUDA source into GPU and CPU code, sending GPU code to the GPU compiler which generates PTX assembly language" ([NVIDIA, Understanding PTX](https://developer.nvidia.com/blog/understanding-ptx-the-assembly-language-of-cuda-gpu-computing/)). PTX is "a versioned virtual machine ISA that enables forward compatibility by allowing the NVIDIA GPU driver to JIT compile PTX to cubin binaries for GPUs released after the application was built". The specification's own words: "PTX defines a virtual machine and ISA for general purpose parallel thread execution" and aims to "Provide a stable ISA that spans multiple GPU generations" ([PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/)). Then "This assembly (PTX) is then run through an assembler, called ptxas, which generates executable binary code for the GPU", and that binary's instruction set is SASS, specific to one chip generation.

So: CUDA C++ is the source, PTX is the portable assembly, SASS is the machine code. On Apple the equivalent chain is MSL to a private intermediate form to machine code, and only the first is documented. Week 4 day 2's applegpu exists because Apple publishes no SASS.

**Reading what the compiler did.** Two tools: "cuobjdump accepts both cubin files and host binaries while nvdisasm only accepts cubin files; but nvdisasm provides richer output options" ([CUDA binary utilities](https://docs.nvidia.com/cuda/cuda-binary-utilities/index.html)). The reason to read PTX, from a Hopper worklog: "Unfortunately, there's no documentation of these instructions in CUDA C++ guide and we have to look at PTX guide" ([Shankhdhar](https://cudaforfun.substack.com/p/outperforming-cublas-on-h100-a-worklog)). The newest hardware instructions arrive in PTX before they have C++ names, so the people pushing H100s and B200s write inline PTX. That is the layer tomorrow and the day after live at.

**Triton, the layer most AI-written kernels use.** Triton is a Python language for GPU kernels built on a different idea: "programming paradigms based on blocked algorithms can facilitate the construction of high-performance compute kernels for neural networks". Its documentation contrasts the "CUDA Programming Model (Scalar Program, Blocked Threads)" with the "Triton Programming Model (Blocked Program, Scalar Threads)" ([Triton introduction](https://triton-lang.org/main/programming-guide/chapter-1/introduction.html)). In CUDA you write what one thread does and the hardware groups them. In Triton you write what one block of data does and the compiler decides the threads. The compiler's work is visible: a GPU MODE lecture on Triton internals shows the artifacts, "dict_keys(['llir', 'ttgir', 'ttir', 'ptx', 'cubin'])", and the pipeline "Python DSL ➡️ IR ➡️ PTX ➡️ CUBIN/fatbinary ➡️ launcher.so" ([GPU MODE lecture 29](https://raw.githubusercontent.com/gpu-mode/lectures/main/lecture_029/presentation.md)). One line in that deck is the lesson for a director: `passes.ttgpuir.add_pipeline(pm, opt.num_stages)`. The pipelining depth you set is handed to a compiler pass; it is a knob, not a fact about the hardware. Triton is what the FLA linear-attention library from week 6 day 4 is written in, and it is the layer a benchmark in week 6 day 1 shows losing 2.7x to hand-written code on a B200.

**CUTLASS and CuTe, the layer the record holders use.** NVIDIA's template library: "CUTLASS 3.0 introduces a new core library, CuTe, to describe and manipulate tensors of threads and data", with "Support for NVIDIA Hopper GPUs with great performance using features such as Tensor Cores, tensor memory accelerator, and thread block clusters", and the design claim that "Layouts provide a single point of performance tuning, as most optimizations can be done by careful selection of thread and data layouts" ([CUTLASS 3.x design](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/cutlass_3x_design.html)). FlashAttention-4 is "entirely in CuTe-DSL embedded in Python, achieving 20-30× faster compile times compared to traditional C++ template-based approaches" ([FlashAttention-4](https://proceedings.mlsys.org/paper_files/paper/2026/file/ae8b0b5838ba510daff1198474e7b984-Paper-Conference.pdf)). The newest layer, CUDA Tile, "extends CUDA's low-level programming model with new abstractions that differ from what has previously existed in CUDA C++ or PTX", shipped "aligned with the CUDA Toolkit 13.1 release" ([CUDA Tile](https://github.com/NVIDIA/cuda-tile)). It is Triton's block idea, adopted by NVIDIA.

**For the director.** Each layer trades control for portability. CUDA C++ with inline PTX gets the newest instructions and is tied to one chip generation; the Hopper kernels in two days break on Blackwell. Triton is portable and readable, and an AI writes it fluently, but it leaves 2x to 3x on the table on the newest chips. CuTe is where the records are set and the hardest to read. On Apple you had no such choice: MLX gives you MSL, and the only knob beneath it is the body you write. When an AI proposes an NVIDIA kernel, the first question is which layer, because that sets the ceiling before any tuning.
