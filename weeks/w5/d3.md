# Week 5, day 3 · The matmul ladder on NVIDIA

**Why this day.** Week 2 day 3 used Simon Boehm's ladder for the universal steps. Today is the full NVIDIA story: how far the ladder goes on an Ampere-class card, what it costs in time, and the moment it stops working on Hopper.

## The story

**The ladder, with its author's own account.** Boehm's goal: "I'll start with a naive kernel and step-by-step apply optimizations until we get within 95% (on a good day) of the performance of cuBLAS (NVIDIA's official matrix library)" ([siboehm](https://siboehm.com/articles/22/CUDA-MMM)). The card was an A6000, "advertised as being able to achieve almost 30 TFLOPs", with 768 GB/s of memory bandwidth. The ten kernels, FP32, 4092 by 4092:

| Kernel | GFLOPS | Percent of cuBLAS |
|---|---|---|
| 1 Naive | 309.0 | 1.3% |
| 2 Global memory coalescing | 1,986.5 | 8.5% |
| 3 Shared memory caching | 2,980.3 | 12.8% |
| 4 1D block tiling | 8,474.7 | 36.5% |
| 5 2D block tiling | 15,971.7 | 68.7% |
| 6 Vectorized memory access | 18,237.3 | 78.4% |
| 9 Autotuning | 19,721.0 | 84.8% |
| 10 Warp tiling | 21,779.3 | 93.7% |
| cuBLAS | 23,249.6 | 100% |

Kernels 7 and 8 are skipped in the post. The time: "It took me two weekends to write the first 6 kernels which reach 80% of peak FLOPs, and then 4 more weekends to do autotuning and warptiling to get to 94%." The last 14 percent cost twice as long as the first 80.

**Each rung as a byte count.** The naive kernel reads every input value from global memory once per use. Coalescing makes neighbouring threads read neighbouring addresses, which is yesterday's 13x lesson in the other direction. Shared-memory caching loads a tile once for a whole thread block. Block tiling makes each thread compute several outputs so the values it loaded are reused from registers; "We'll continue optimizing arithmetic intensity for as long as we're still memory bound." Vectorized access loads four floats per instruction, week 2's float4. Autotuning sweeps the tile sizes. Warp tiling arranges the work so that the 32 threads of a warp reuse what they load together: "Warptiling is somewhat confusing initially since unlike blocks and threads, warps don't show up anywhere in the CUDA code explicitly. They are a hardware feature that has no direct analog in the CUDA programming model." Boehm's measure of the whole climb: "The cuBLAS kernel loads a total of 500MB of GMEM during the whole calculation", against a theoretical minimum of 268 MB, reaching "~245 FLOPs/Byte". Every rung is a reduction in bytes per operation, which is the roofline's x-axis.

**Why the library is still ahead.** "cuBLAS contains not one single implementation of SGEMM, but hundreds of them", selected per shape. And the library has a door the ladder does not use: switching to tensor cores "increases FLOPS by 2.5x or 3.5x" on the same card. The ladder is FP32 on ordinary cores; the real matmuls run in 16-bit on the matrix units.

**The 2008 result that still holds.** Volkov and Demmel's GEMM "runs up to 60% faster than the vendor's implementation and approaches the peak of hardware capabilities", and their explanation was a reframing: "modern GPUs should be viewed as multithreaded multicore vector units" ([Volkov SC08](https://mc.stanford.edu/cgi-bin/images/6/65/SC08_Volkov_GPU.pdf)). Their occupancy finding is the one to keep: "one should not over-optimize for the occupancy, although extremely low occupancy may also hurt." The best kernel used few threads with many registers each. Boehm's warp tiling is the same conclusion on a card fifteen years newer.

**Where the ladder ends.** Pranjal Shankhdhar took Boehm's final kernel to an H100 and reported that it "is only able to achieve 4% of cuBLAS performance" ([Shankhdhar](https://cudaforfun.substack.com/p/outperforming-cublas-on-h100-a-worklog)). Gordic says why: "this style of kernel is no longer the method of choice — modern GPUs have asynchronous memory mechanisms and tensor cores that push performance far beyond" what the ladder reaches ([Gordic](https://www.aleksagordic.com/blog/matmul)). A kernel at 94 percent of the library on one generation is at 4 percent on the next, because the next generation's library uses units the kernel never touches. Tomorrow is the new ladder.

**For the director, and for Apple.** The ladder's first five rungs, coalescing through 2D tiling, are the universal part and apply on an M5. The shared-memory rung is the one Apple's guide drops. Warp tiling maps to simdgroup tiling and the 8 by 8 matrices. And the ending is the same on both platforms: the M5's neural accelerators, like Hopper's tensor cores, are a unit the old ladder does not reach, which is why week 3 day 2's split-K story exists. When an AI shows you a matmul kernel, ask which rung it is on and which units it uses; those two answers bound its speed before you run it.
