# Week 1, day 2 · The GPU core

**Why this day.** A kernel's threads run inside one GPU core, with the core's registers, scratch memory, and caches. The sizes of those three, and the way the core keeps itself busy while waiting for memory, decide what shape a fast Apple kernel has. This page is the inside of one core, with the numbers that are measured, the ones Apple states, and the ones nobody knows.

## How it works

**Threads, in bundles.** A GPU does not run one thread at a time the way a CPU core does. It runs a group of 32 threads in lockstep: one instruction, 32 copies, on 32 different data items, in one step. Apple's name for the group is a SIMD-group, written simdgroup in code. The community measurements in philipturner/metal-benchmarks describe the core's issue machinery: "The Apple GPU core has four schedulers, each dispatching one instruction from one simd (32 threads) per cycle" ([metal-benchmarks](https://github.com/philipturner/metal-benchmarks)). MLX carries the same number as a constant, `MLX_MTL_CONST int SIMD_SIZE = 32;`.

Simdgroups are bundled into threadgroups. A threadgroup is the unit the hardware hands to a core: all its threads run on the same core, and they can share a small scratch memory. Apple's limits: "Threadgroups can have up to 1024 threads per threadgroup" and "threads can share up to 32K of threadgroup memory" ([WWDC22 session 10159](https://developer.apple.com/videos/play/wwdc2022/10159/)). A launch is a grid of threadgroups; the GPU distributes them across its cores.

```
grid (one launch)
 ├─ threadgroup ────────── goes to one core, up to 1,024 threads, 32 KB shared scratch
 │   ├─ simdgroup ──────── 32 threads in lockstep; can pass values lane to lane
 │   │   ├─ thread
 │   │   └─ ... 32
 │   └─ ... up to 32 simdgroups
 └─ ... thousands of threadgroups
```

**Three memories inside the core.** Each thread has registers, the fastest storage there is, private to that thread. Each threadgroup has its scratch, the threadgroup memory. Behind both is a cache that holds recently used lines from the big memory. Measured on the M1 and M2 cores:

| | Apple core, measured M1/M2 | NVIDIA H100 SM, published |
|---|---|---|
| Register file | about 208 KB | 256 KB |
| Shared scratch | about 60 KB per core; 32 KB per threadgroup | 228 KB |
| Data cache | 8 KB | shares a 256 KB pool with scratch |

The Apple numbers are from metal-benchmarks: "| Register File | ~208 KB |", "| Shared Memory | ~60 KB |", "| Data Cache | 8 KB |", with the author's reading: "Apple GPUs have much smaller data caches than other vendors. The L1 is 8 KB" and "The larger register size makes up for the smaller lower-level cache sizes." The NVIDIA numbers are from week 5 day 1. The shape is reversed. NVIDIA gives a kernel a large programmer-managed scratch and a large cache; Apple gives it large registers and little else. Every design rule on this platform follows from that: keep working values in registers, treat threadgroup memory as a small staging area, do not plan on the cache holding a tile for you.

Two of Apple's numbers look inconsistent and are not. 32 KB is the most one threadgroup may use; about 60 KB is the pool on the core that several threadgroups draw from at once.

**Why the core needs many simdgroups.** A load from the memory chips takes hundreds of cycles. A simdgroup that has asked for a value can do nothing until it arrives. The core hides that by holding several simdgroups and switching to one that is ready. Apple's term: "The number of SIMDgroups that are concurrently running on a shader core is called its thread occupancy" ([tech talk 111375](https://developer.apple.com/videos/play/tech-talks/111375/)). High occupancy means the core always has something to issue. Low occupancy means it idles between loads, which is why the week 2 roofline is only reachable with enough threads in flight.

What limits occupancy is the register file. Each resident simdgroup needs its registers allocated. Before the M3, "a SIMDgroup could not begin execution on a shader core until it allocated registers from the on-chip register file", and "The amount allocated would be equal to the maximum register usage at any point in the program." One line in a kernel that briefly needed 128 registers per thread made the whole kernel cost 128 registers per thread for its whole life, which cut how many simdgroups fit.

**What the M3 changed.** "On-chip register memory is now dynamically allocated and deallocated over the lifetime of the shader according to what each part of the program actually uses", because "the register file is now a cache instead of the permanent storage for the registers". Apple extended that to the scratch too: "The flexible on-chip memory feature extends this treatment to the rest of the shader core's memory types, such as threadgroup and tile memory, making that a cache too", by redesigning "the on-chip memories into fewer larger caches that service all these memory types". The marketing name is Dynamic Caching, which "allocates the use of local memory in hardware in real time" ([Apple, M3](https://www.apple.com/newsroom/2023/10/apple-unveils-m3-m3-pro-and-m3-max-the-most-advanced-chips-for-a-personal-computer/)); the M5 has a "rearchitected second-generation dynamic caching". Apple's conclusion for you: "you, the developer, need to optimize occupancy a lot less often than in the past."

## Worked example: how many threads fill the machine

Your M5 has 10 cores. Apple's rule of thumb from the WWDC22 talk is that "1K to 2K concurrent threads per shader core is considered a very good occupancy". So the machine wants 10,000 to 20,000 threads in flight.

A kernel that sums the rows of a 2,000 by 4,000 matrix with one simdgroup per row launches 2,000 × 32 = 64,000 threads: full. The same bytes arranged as 2 rows of 4,000,000 launch 64 threads: two simdgroups, at most two cores busy, each one stalling on every load with nothing to switch to. Measured in the first version of this course on an M5, the second shape ran 59 times slower than the first on the same 32 MB. That is occupancy, seen from outside.

## What is not known

Everything measured above is from the M1 and M2. Apple publishes no register or cache sizes, and metal-benchmarks stopped at the M2 and was last pushed in September 2024. For an M3, M4, or M5 the only honest statements are directional: registers large, caches small, allocation dynamic. Any exact figure an AI gives you for an M5 core is a guess unless it comes with a measurement.
