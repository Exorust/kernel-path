# Week 1, day 2 · The GPU core

**Why this day.** Yesterday was the chip from the outside. Today is the inside of one GPU core, which is where a kernel's threads actually run, where its registers live, and where the choices that make Apple different from NVIDIA come from.

## The story

A GPU core runs threads in groups of 32. Apple's name for that group is a SIMD-group, written simdgroup in code. The community measurements in philipturner/metal-benchmarks describe the core this way: "The Apple GPU core has four schedulers, each dispatching one instruction from one simd (32 threads) per cycle" ([metal-benchmarks](https://github.com/philipturner/metal-benchmarks)). MLX's own kernels carry the same number as a constant: `MLX_MTL_CONST int SIMD_SIZE = 32;`.

Threads are bundled further into threadgroups, which is the unit the hardware hands to a core. Apple's limits, from the WWDC22 compute talk: "Threadgroups can have up to 1024 threads per threadgroup" and "threads can share up to 32K of threadgroup memory" ([WWDC22 session 10159](https://developer.apple.com/videos/play/wwdc2022/10159/)). Threadgroup memory is the small scratch space the threads of one group share.

**The memory inside a core, and why it is upside down compared with NVIDIA.** metal-benchmarks measured the M1 and M2 cores and found a register file of about 208 KB, shared memory of about 60 KB, a data cache of 8 KB, and an instruction cache of 12 KB. Its summary: "Apple GPUs have much smaller data caches than other vendors. The L1 is 8 KB" and "The larger register size makes up for the smaller lower-level cache sizes." On NVIDIA the design leans the other way, with large shared memory per core and a large cache behind it. The practical rule that follows, and that every Apple kernel in this course obeys: keep working data in registers, use threadgroup memory as a small staging area, and do not plan on the cache.

Two numbers look like they disagree. Apple says 32K of threadgroup memory per threadgroup. metal-benchmarks measured about 60 KB of shared memory per core. They are different quantities: one is the limit for a single threadgroup, the other is the pool on the core that several threadgroups share. Keep both.

One more measurement to carry: "On bandwidth bound tasks, the GPU has no advantage over the CPU. Because its I/O bus width is the same (32 bytes)" (metal-benchmarks). For work that only moves bytes, the GPU and the CPU are drinking from the same pipe.

**Occupancy, and what the M3 changed.** Occupancy is "the number of SIMDgroups that are concurrently running on a shader core" ([Apple tech talk 111375](https://developer.apple.com/videos/play/tech-talks/111375/)). It matters because a simdgroup that is waiting for memory does nothing; the core hides that wait by running another one. Before the M3, a simdgroup "could not begin execution on a shader core until it allocated registers from the on-chip register file", and the amount was "equal to the maximum register usage at any point in the program". A kernel with one register-hungry line paid for it everywhere, by lowering how many simdgroups fit.

The M3 generation changed this. "On-chip register memory is now dynamically allocated and deallocated over the lifetime of the shader according to what each part of the program actually uses", because "the register file is now a cache instead of the permanent storage for the registers". Apple extended the same idea to threadgroup memory, redesigning "the on-chip memories into fewer larger caches that service all these memory types". Apple's marketing name for this is Dynamic Caching, which "unlike traditional GPUs, allocates the use of local memory in hardware in real time" ([Apple, M3](https://www.apple.com/newsroom/2023/10/apple-unveils-m3-m3-pro-and-m3-max-the-most-advanced-chips-for-a-personal-computer/)); the M5 has a "rearchitected second-generation dynamic caching". The consequence Apple draws: "you, the developer, need to optimize occupancy a lot less often than in the past."

**What is and is not known.** Everything measured above is from M1 and M2. Apple publishes no per-core sizes, and metal-benchmarks stopped at M2 and was last updated in September 2024. For an M3, M4, or M5, the register and cache figures are unverified, and the only honest statement is the direction: registers large, caches small, and allocation now dynamic.

## The primary source

The transcript of Apple's tech talk ["Explore GPU advancements in M3 and A17 Pro"](https://developer.apple.com/videos/play/tech-talks/111375/), from about 4:46 to 16:10, about 15 minutes. It is the best plain-language Apple text on occupancy and on why the register file became a cache.

## Numbers to remember

| | |
|---|---|
| Simdgroup | 32 threads, every Apple GPU |
| Threadgroup limits | 1,024 threads, 32 KB of threadgroup memory |
| Core memories, M1/M2 measured | ~208 KB registers, ~60 KB shared, 8 KB data cache |
| Occupancy | simdgroups resident on a core at once; dynamic since M3 |
