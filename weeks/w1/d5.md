# Week 1, day 5 · Threads and memory inside a kernel

**Why this day.** Day 2 was the core from the hardware's side. Today is the same structure from inside a kernel: how a thread learns where it is, how 32 threads combine a value without touching memory, how a threadgroup shares scratch safely, and the one rule that keeps parallel writes from corrupting each other. These are the moves every kernel in weeks 2 and 3 is built from.

## How it works

**Who am I.** A kernel body runs once per thread, and the only thing that differs between threads is their position. Metal supplies it through attributes on arguments; table 5.8 of the specification lists them. The ones you will use, with what each gives:

| Name | Type | Meaning |
|---|---|---|
| `thread_position_in_grid` | `uint`, `uint2`, or `uint3` | this thread's position in the whole launch |
| `thread_position_in_threadgroup` | same | position inside its threadgroup |
| `threadgroup_position_in_grid` | same | which threadgroup this is |
| `thread_index_in_threadgroup` | `uint` | flat index inside the threadgroup |
| `thread_index_in_simdgroup` | `uint` | the lane, 0 to 31 |
| `simdgroup_index_in_threadgroup` | `uint` | which simdgroup inside the threadgroup |
| `threads_per_simdgroup` | `uint` | 32 on every Apple GPU |

The specification gives the arithmetic for one of them: "the thread index in the threadgroup (thread_index_in_threadgroup) is determined by: ly * Sx + lx", the row-major flattening of the threadgroup's position. It also gives a warning worth keeping: "Within a threadgroup, threads are divided into SIMD-groups in an implementation-defined fashion. Any given thread in a SIMD-group can query its SIMD lane ID and which SIMD-group it is a member of." On an M5, measured by running kernels, the lane equals the grid position modulo 32 and the simdgroup index is the position within the threadgroup divided by 32. Treat that as a measurement, not a guarantee, and always ask for the lane by name rather than computing it.

In an MLX kernel body you just use the name; MLX adds the argument to the generated function when it sees it. Apple's description of the picture: "Each point in the grid represents a thread, which is a single instance of your kernel function" ([Creating threads and threadgroups](https://developer.apple.com/documentation/metal/creating-threads-and-threadgroups)).

**A grid with two dimensions.** Most kernels in this course launch a 2D grid, `grid=(32, rows, 1)` with `threadgroup=(32, 1, 1)`. Then `thread_position_in_grid.x` is the lane, 0 to 31, and `.y` is the row, and each row of the problem gets one simdgroup. The mlx-lm linear-attention kernel from week 3 day 3 launches `grid=(32, Dv, B * Hv)` with `threadgroup=(32, 4, 1)`, so `.x` is the lane, `.y` the state row, and `.z` the batch and head. The shape of the grid is the plan of the kernel.

**The 32 lanes combine without memory.** The threads of a simdgroup execute in lockstep, so the hardware can pass values between them in one instruction. Apple's A14 talk defines the one you will use most: "simd_sum adds up values of a variable across all active threads in the SIMD group and broadcasts the sum back to all the threads" ([tech talk 10858](https://developer.apple.com/videos/play/tech-talks/10858/)). After `float total = simd_sum(v);` every one of the 32 lanes holds the same total. Its relatives: `simd_max`, `simd_min`, `simd_prefix_inclusive_sum` for a running sum, and `simd_shuffle_xor(v, m)`, which gives each lane the value held by the lane whose number differs in the bits of `m`. On Apple these are fast: your glossary records "256 B/cycle of shuffle bandwidth per core, double what contemporary NVIDIA and AMD parts move", so "kernels here reach for `simd_shuffle_xor` reductions without hesitation" ([simdgroup](https://metalworking.vercel.app/machine/simdgroup/)). Week 2 day 2 shows MLX's reductions doing exactly this for their first 32-wide stage.

**One writer.** Threads run at the same time in no fixed order. Two threads writing the same element of an output is a race, and the result is whichever landed last. After a `simd_sum` all 32 lanes hold the answer, so the pattern is `if (thread_index_in_simdgroup == 0) out[row] = total;`: one lane stores. The same rule holds at every level: a thread writes its own element and nothing else, unless a reduction or a barrier says otherwise.

**Scratch shared by a threadgroup.** When threads of one threadgroup must exchange more than a simdgroup can shuffle, they use threadgroup memory: declare it, write it, wait, read what others wrote.

```metal
threadgroup float buf[TG];                          // scratch for this threadgroup
uint t = thread_index_in_threadgroup;
buf[t] = a[thread_position_in_grid.x];              // every thread deposits one value
threadgroup_barrier(mem_flags::mem_threadgroup);    // wait until every thread has
out[thread_position_in_grid.x] = buf[TG - 1 - t];   // read a value another thread wrote
```

The barrier is the point: without it a thread may read `buf[k]` before the thread that owns `k` has written it. The specification's term for the scratch is the threadgroup address space, "faster on most devices than sharing data in device memory", limited by day 2's 32 KB. MLX's row reduction does the two-stage pattern: `simd_sum` within each simdgroup, then one value per simdgroup into a tiny threadgroup array, a barrier, and a final `simd_sum` across those ([MLX reduce_row.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/reduction/reduce_row.h)).

## Worked example: the sum of every row

A matrix with 2,000 rows of 4,000 floats. One simdgroup per row.

```metal
uint lane = thread_position_in_grid.x;          // 0 to 31
uint row  = thread_position_in_grid.y;          // which row this simdgroup owns
float acc = 0.0f;                               // private: a register
for (uint c = lane; c < COLS; c += 32)          // lane 0 takes columns 0, 32, 64 ... lane 1 takes 1, 33, 65 ...
    acc += W[row * COLS + c];                   // the matrix is flat: row r starts at r * COLS
float total = simd_sum(acc);                    // 32 partial sums become one, in every lane
if (lane == 0) out[row] = total;                // one writer
```

Why lane `l` takes columns `l, l+32, l+64`: at every step of the loop the 32 lanes read 32 neighbouring floats, one contiguous block of 128 bytes, which is the access pattern memory delivers fastest. If each lane took a contiguous run of 125 columns instead, every step would touch 32 addresses 500 bytes apart. The first version of this course measured both on an M5 and found them within noise at this size, which says the hardware tolerates both here; week 2 day 2 shows the same choice costing 5x on another kernel. The habit is to make neighbouring lanes touch neighbouring addresses and then measure.

The plan for this kernel is the shape of week 1 Wednesday's matrix-vector product in the old course and of the week 3 day 3 linear-attention scan: one simdgroup owns one row, the state lives in registers, the lanes reduce with one instruction, one lane stores.
