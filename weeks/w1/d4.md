# Week 1, day 4 · MLX

**Why this day.** MLX is where you will actually work. It hides yesterday's seven Metal objects behind Python arrays, decides when kernels run, and gives you one door, `mx.fast.metal_kernel`, for a kernel of your own. Understanding what MLX does for you is what lets you tell an AI exactly what to write.

## The story

"MLX is an open source array framework purpose-built for Apple Silicon" ([WWDC25 session 315](https://developer.apple.com/videos/play/wwdc2025/315/)). It is written by Apple's machine-learning research group, released under an MIT license, with APIs in Python, C++, and C. On GitHub on 2026-10-08 it had 28,696 stars; the text-generation package built on it, mlx-lm, had 7,254; the vision-language package mlx-vlm had 5,589. For comparison, llama.cpp, the other engine that runs models on Apple GPUs, had 130,546.

**Three ideas explain how it runs your code.**

*Unified memory, seen from Python.* "In MLX, arrays are allocated in unified memory" (WWDC25). The docs put the consequence this way: "rather than moving arrays to devices, you specify the device when you run the operation" ([MLX unified memory doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/usage/unified_memory.rst)). There is no `.to("gpu")` because there is nowhere to move to.

*Lazy evaluation.* "When you perform operations in MLX, no computation actually happens. Instead a compute graph is recorded. The actual computation only happens if an eval() is performed" ([MLX lazy evaluation doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/usage/lazy_evaluation.rst)). Calling a kernel returns at once; the GPU runs when a result is needed or when you call `mx.eval`. The talk gives the upside: "with lazy computation, you only ever pay for what you use." The cost, which matters for every timing you will ever read, is that a loop which forgets to evaluate measures nothing.

*How an op becomes a kernel.* "Operations in MLX build the computation graph. Primitives provide the rules for evaluating and transforming the graph." Each primitive "has methods to run on the CPU or GPU", named `eval_gpu` in the source, and the GPU method launches a Metal kernel ([MLX extensions doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/dev/extensions.rst)). The matrix kernels live in a library inside MLX called steel, built from yesterday's 8 by 8 simdgroup matrices: each of the 32 lanes holds 2 of the 64 elements, `kElemsPerFrag = (kFragRows * kFragCols) / 32`.

**Where the speed knobs are.** Each node of the graph "corresponds to a separate GPU Kernel launch under the hood", and "Compiling the graph uses all of these separate Kernels into single fused Kernel" (WWDC25 transcript; the speaker almost certainly said "fuses"). That is `mx.compile`: "The first time you call a compiled function, MLX will build the compute graph, optimize it, and generate and compile code. This can be relatively slow. However, MLX will cache compiled functions" ([compile doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/usage/compile.rst)). Fewer launches is the first lever in week 3 day 5.

The second lever is `mx.fast`, "the mx.fast sub-package, which has off-the-shelf fast implementations of common machine learning operations, and an API for adding your own custom Metal Kernels" (WWDC25). The fast ops are rms_norm, layer_norm, rope, scaled_dot_product_attention, and the two custom-kernel entries, metal_kernel and precompiled_cuda_kernel ([fast.rst](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/python/fast.rst)). These are the hand-written kernels the MLX team already tuned; most of the speedup stories in week 3 are about getting a model onto one of them.

**Your door.** `mx.fast.metal_kernel` takes the body of a Metal kernel as a string. The rule that trips everyone: "Only pass the body of the Metal kernel in ``source``. The function signature is generated automatically" ([custom kernels doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/dev/custom_metal_kernels.rst)). You pass input names, output names, the body, the grid size, and the threadgroup size; MLX writes the function header, compiles it, launches it, and hands back an array. "You write the custom Kernel and MLX handles all the rest, including just-in-time compilation and execution", and "MLX treats the Kernel call the same way as any other operation" (WWDC25). Every custom kernel in this course is a body string and two tuples.

**The ecosystem around it.** mlx-lm is "a Python package for generating text and fine-tuning large language models on Apple silicon with MLX", with "Integration with the Hugging Face Hub" and "Distributed inference and fine-tuning with `mx.distributed`" ([mlx-lm README](https://github.com/ml-explore/mlx-lm)). The other engine is llama.cpp, whose README says "Apple silicon is a first-class citizen - optimized via ARM NEON, Accelerate and Metal frameworks" ([llama.cpp](https://github.com/ggml-org/llama.cpp)); its Metal kernels live under `ggml/src/ggml-metal/kernels/`. Core ML and the Neural Engine are a third path, not covered here because they are not programmable at the kernel level.

A young-framework story worth knowing: MLX issue #243, filed 2023-12-21, "PyTorch (MPS) is faster than MLX for training and inference for ResNets and Transformers", measured on an M1 ([issue](https://github.com/ml-explore/mlx/issues/243)). Two years later the fast kernels in week 3 are the answer.
