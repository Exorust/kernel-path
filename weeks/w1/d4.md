# Week 1, day 4 · MSL, the language

**Why this day.** Every kernel body you will read or direct is written in the Metal Shading Language. It is C++ with things removed and a dozen GPU words added. After today you can read any kernel body line by line and say what each line does, which is the one skill that lets you judge what an AI hands you.

## How it works

**The base.** The specification: "In Metal 4 and later, the Metal programming language is a C++17-based specification with extensions and restrictions. … Prior language versions of Metal are a C++14-based specification" ([MSL specification 4.1](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)). If you can read C, you can read a kernel body. Variables, arithmetic, comparisons, `if`, `for`, `while`, the ternary `? :`, arrays, pointers, casts, functions, and templates all work as in C++.

**What is removed.** From section 1.5.4 of the specification: no `dynamic_cast`, no `new` and `delete` (placement `new` arrived in Metal 4.1), no `goto`, no `virtual` functions, no derived classes, no exceptions, and "Do not use the C++ standard library in Metal code. Instead, Metal has its own standard library." Two more that bite in practice, both confirmed by compiling them on an M5 through MLX: `double` is rejected with "'double' is not supported in Metal", and `printf` does not exist. To see a value from inside a kernel, write it to an output array. Recursion is allowed in compute code since Metal 2.4, and function pointers since 2.3, so those two old rules of thumb are wrong now.

**Numbers.** The scalar types from section 2.1: `bool`; `char` and `uchar` at 8 bits; `short` and `ushort` at 16; `int` and `uint` at 32; `long` and `ulong` at 64 since Metal 2.2; `half`, a 16-bit float; `bfloat`, the 16-bit brain float since Metal 3.1; and `float`. "Metal does not support the double, long long, unsigned long long, and long double data types." Literal suffixes: `0.5f` is a float, `0.5h` a half, `0.5bf` a bfloat, `1u` an unsigned integer. A float literal without the `f` also compiles; writing the `f` makes the type explicit, which matters in a language with no double for it to become. Whole-number division drops the remainder, `7 / 2` is `3`, and `%` gives the remainder. A `uint` below zero wraps: `0u - 1` is 4,294,967,295, a bug that shows up as a huge index.

**Vectors.** `float2`, `float3`, `float4`, and the same for `half`, `int`, `uint`, `short`, `uchar`, plus `bfloat` since 3.1; or `vec<T, n>`. The parts are `.x .y .z .w`. Arithmetic on a vector acts on every part. The reason to care: `float4` loads four floats in one instruction and `half4` loads four halves, which is how a kernel reads 16 bytes per thread per step. In an MLX kernel body the load is a pointer cast, `float4 v = *((const device float4*)(a + 4 * i));`, verified to work.

**Casts.** Function style, `float(i)`, or C style, `(float)i`. The pattern you will see constantly: read a `half`, cast to `float`, do the arithmetic in 32 bits, cast back to store. Accumulating in `half` loses precision; week 1 of the old course measured a thousand-fold accuracy difference between a hand-written kernel that accumulated in float and MLX's half matmul.

**Functions that exist.** Metal's own library: `sqrt`, `exp`, `log`, `abs`, `min`, `max`, `clamp`, `fma`, `dot`, `floor`, `pow`, and the simdgroup family from tomorrow, `simd_sum`, `simd_max`, `simd_shuffle_xor`, `simd_prefix_inclusive_sum`. They live in a namespace called `metal`; inside an MLX kernel body you can call them bare, `exp(x)`, or qualified, `metal::exp(x)`. Both compile.

**Where a value lives: the address spaces.** This is the one idea that has no C equivalent and that every pointer must declare. Section 4: "All arguments to a graphics or kernel function that are a pointer or reference to a type needs to be declared with an address space attribute", and "If an address space attribute is missing on a pointer or reference type declaration, a compilation error occurs." The four you will meet:

| Word | What it is | Apple's definition |
|---|---|---|
| `device` | the big memory; your arrays | "buffer memory objects allocated from the device memory pool that are both readable and writeable" |
| `constant` | the big memory, read-only; small inputs and parameters | "buffer memory objects allocated from the device memory pool that are read-only" |
| `threadgroup` | the scratch one threadgroup shares | "Threads in a threadgroup can work together by sharing data in threadgroup memory, which is faster on most devices than sharing data in device memory" |
| `thread` | a variable inside the kernel, private to one thread; in practice a register | "the per-thread memory address space. Variables allocated in this address space are not visible to other threads. Variables declared inside a graphics or kernel function are allocated in the thread address space." |

You write `device` and `constant` on function arguments, `threadgroup float buf[64];` to declare scratch, and nothing at all for an ordinary `float x` inside the body, which is `thread` by default.

**Attributes.** The double brackets, `[[...]]`, are labels that tell Metal what an argument is for. `[[kernel]]` marks the function. `[[buffer(0)]]` ties a pointer to the first array passed in. `[[thread_position_in_grid]]` asks Metal to fill in this thread's position. Tomorrow's page has the full table.

## Worked example: a kernel body, line by line

This is the body MLX wraps for an elementwise exponential, from MLX's own documentation, with the function MLX generates around it:

```metal
template <typename T>
[[kernel]] void custom_kernel_myexp_float_float16_t_float16_t(
  const device float16_t* inp [[buffer(0)]],
  device float16_t* out [[buffer(1)]],
  uint3 thread_position_in_grid [[thread_position_in_grid]]) {
      uint elem = thread_position_in_grid.x;
      T tmp = inp[elem];
      out[elem] = metal::exp(tmp);
}
```

- `template <typename T>`: the type `T` is chosen when the kernel is built, from the `template=` argument.
- `const device float16_t* inp [[buffer(0)]]`: a read-only pointer into the big memory, tied to the first input. `float16_t` is MLX's name for `half`.
- `uint3 thread_position_in_grid`: three unsigned integers, this thread's x, y, z position; Metal fills it in because of the attribute.
- `uint elem = thread_position_in_grid.x;`: my element, a private `thread` variable.
- `T tmp = inp[elem];`: one load from device memory.
- `out[elem] = metal::exp(tmp);`: one built-in call, one store.

Three lines of body. Everything above the brace is what MLX writes. Day 6 shows how to make MLX print this for any kernel you give it.

**Reading a compile error.** The Metal compiler's messages are clang's. A missing semicolon in an MLX kernel body produces, at the moment the result is first needed:

```
[metal::Device] Unable to build metal library from source
...error: expected ';' at end of declaration
uint i = thread_position_in_grid.x
                                  ^
                                  ;
```

The first line names the problem, the next is your line, the caret marks the spot. MLX raises it as a Python `RuntimeError` when the array is evaluated, not when the kernel is created, because of the lazy evaluation on day 6.

| | |
|---|---|
| Base | C++17, since Metal 4 |
