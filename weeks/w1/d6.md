# Week 1, day 6 · MLX

**Why this day.** MLX is where you will actually work. It hides day 3's seven objects behind Python arrays, decides when kernels run, ships the hand-tuned kernels that weeks 2 and 3 are about, and gives you one door for a kernel of your own. Knowing what MLX does for you is what lets you tell an AI exactly what to write and what not to.

## How it works

**What it is.** "MLX is an open source array framework purpose-built for Apple Silicon" ([WWDC25 session 315](https://developer.apple.com/videos/play/wwdc2025/315/)), written by Apple's machine-learning research group, "open source under a permissive MIT license", with "APIs in C++ and C" beside Python. On 2026-10-08 it had 28,696 GitHub stars; mlx-lm, the text-generation package on top of it, 7,254; mlx-vlm, for vision-language models, 5,589. llama.cpp, the other engine that runs models on Apple GPUs, had 130,546.

**Idea one: arrays live in unified memory.** "In MLX, arrays are allocated in unified memory" (WWDC25). The documentation's consequence: "In MLX, rather than moving arrays to devices, you specify the device when you run the operation" ([unified memory doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/usage/unified_memory.rst)). There is no `.to("gpu")` because day 1 said there is nowhere to move to. An operation takes a `stream` argument that says which engine runs it, CPU or GPU, on the same bytes.

**Idea two: nothing runs until you ask.** "When you perform operations in MLX, no computation actually happens. Instead a compute graph is recorded. The actual computation only happens if an eval() is performed" ([lazy evaluation doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/usage/lazy_evaluation.rst)). Calling `mx.exp(a)` returns at once with an unevaluated array. The GPU runs when a result is needed, when you print, convert, or call `mx.eval`. The upside, from the talk: "with lazy computation, you only ever pay for what you use." The two consequences you will hit:

- A timing loop that never evaluates measures nothing. The first version of this course had a timer bug of exactly this kind, which reported an impossible 4,767 GB/s until each iteration was evaluated.
- A Metal compile error surfaces at evaluation, not at kernel creation, because the kernel is built when the graph runs.

The documentation's rule for loops: evaluating inside a loop "is a bad idea because there is some fixed overhead with each graph evaluation", which is day 3's per-launch cost.

**Idea three: how an op becomes a kernel.** "Operations in MLX build the computation graph. Primitives provide the rules for evaluating and transforming the graph." Each primitive "has methods to run on the CPU or GPU", named `eval_gpu` in the source, and the GPU method encodes a Metal kernel onto a command buffer ([extensions doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/dev/extensions.rst)). So the path is: Python op → graph node → primitive → `eval_gpu` → one of the kernels under `mlx/backend/metal/kernels/` → day 3's command buffer. The matrix kernels are in a sub-library called steel, built from day 3's 8 by 8 simdgroup matrices. When you read "MLX runs a kernel", this is the chain.

**The two speed levers.** The talk: "Each of these nodes corresponds to a separate GPU Kernel launch under the hood", and "Compiling the graph uses all of these separate Kernels into single fused Kernel" (the transcript reads "uses"; the speaker almost certainly said "fuses"). That is `mx.compile`: "The first time you call a compiled function, MLX will build the compute graph, optimize it, and generate and compile code. This can be relatively slow. However, MLX will cache compiled functions" ([compile doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/usage/compile.rst)). The documentation's measurement: a gelu written as a chain of elementwise ops is "overhead bound" on small arrays, and compiled, "On an M1 Max the times are 15.5 and 3.1 milliseconds. The compiled gelu is five times faster." Five launches became one. Week 3 day 5 is this lever at the scale of a whole model.

The second lever is `mx.fast`: "the mx.fast sub-package, which has off-the-shelf fast implementations of common machine learning operations, and an API for adding your own custom Metal Kernels" (WWDC25). The fast ops are `rms_norm`, `layer_norm`, `rope`, `scaled_dot_product_attention`, and the custom-kernel entries `metal_kernel` and `precompiled_cuda_kernel` ([fast.rst](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/python/fast.rst)). These are the hand-written, hand-tuned kernels, and each has a dispatch rule that decides which shapes get the fast path. Week 4 day 4's first question before writing a kernel is whether your shapes are inside one of these gates.

**Your door.** `mx.fast.metal_kernel` takes the body of a Metal kernel as a string. The rule that trips everyone: "Only pass the body of the Metal kernel in ``source``. The function signature is generated automatically" ([custom kernels doc](https://raw.githubusercontent.com/ml-explore/mlx/main/docs/src/dev/custom_metal_kernels.rst)). You give it the input names, output names, the body, and, per call, the grid and threadgroup sizes, the output shapes and types, and any template values. "You write the custom Kernel and MLX handles all the rest, including just-in-time compilation and execution", and "MLX treats the Kernel call the same way as any other operation" (WWDC25). Two switches from the documentation belong in every brief: `verbose=True` prints the generated function, and `ensure_row_contiguous`, true by default, "will copy the array inputs if needed before the kernel is launched", a hidden copy that can double a kernel's bytes.

## Worked example: a custom kernel, call by call

```python
source = """
    uint elem = thread_position_in_grid.x;
    T tmp = inp[elem];
    out[elem] = metal::exp(tmp);
"""
kernel = mx.fast.metal_kernel(
    name="myexp", input_names=["inp"], output_names=["out"], source=source)

outputs = kernel(
    inputs=[a],                       # the array that inp points to
    template=[("T", mx.float32)],     # the type T in the body
    grid=(a.size, 1, 1),              # total threads: one per element
    threadgroup=(256, 1, 1),          # bundled 256 at a time, eight simdgroups
    output_shapes=[a.shape],
    output_dtypes=[a.dtype],
)
```

This is MLX's own example. Map it to the week: the body is day 4's language; `grid` and `threadgroup` are day 2's levels and day 5's launch shape; the generated function with its `[[buffer(0)]]` and `[[thread_position_in_grid]]` is day 4's worked example; and the call runs day 3's seven objects, of which you touched none. The documentation notes that "grid and threadgroup are parameters to the Metal dispatchThreads function", which is day 3's step 6.

**The ecosystem.** mlx-lm is "a Python package for generating text and fine-tuning large language models on Apple silicon with MLX", with "Integration with the Hugging Face Hub" and "Distributed inference and fine-tuning with `mx.distributed`" ([mlx-lm README](https://github.com/ml-explore/mlx-lm)). Its model files are where the linear-attention kernel of week 3 day 3 lives. llama.cpp's README: "Apple silicon is a first-class citizen - optimized via ARM NEON, Accelerate and Metal frameworks" ([llama.cpp](https://github.com/ggml-org/llama.cpp)); its Metal kernels are under `ggml/src/ggml-metal/kernels/`, with the quantized matvec as the largest file. The two engines share the hardware and the week 2 kernel families, and nothing else.

A young-framework story: MLX issue #243, filed 2023-12-21, "PyTorch (MPS) is faster than MLX for training and inference for ResNets and Transformers", on an M1 ([issue #243](https://github.com/ml-explore/mlx/issues/243)). Two years and the `mx.fast` kernels later, the week 3 cases are the answer.
