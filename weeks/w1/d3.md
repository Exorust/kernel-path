# Week 1, day 3 · Metal

**Why this day.** Metal is the only door into the GPU. Even when MLX hides it, every kernel you direct goes through the same seven objects in the same order, and when something is slow or wrong you need to know which step it lives in.

## The story

Metal is Apple's programming interface for the GPU. The language its GPU functions are written in is the Metal Shading Language, MSL, which Apple describes as "a variant of C++ designed for GPU programming" ([Performing Calculations on a GPU](https://developer.apple.com/documentation/metal/performing-calculations-on-a-gpu)). The specification is precise about the base: "In Metal 4 and later, the Metal programming language is a C++17-based specification with extensions and restrictions" ([MSL specification 4.1](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)). A GPU function that does calculation is a kernel. Metal also runs graphics, and the word for any GPU function is shader; the name is historical and means nothing for the work here.

**The path, in the order the objects are used.** Apple's sample walks it end to end, and its sentences are the cleanest description:

1. Device: "Metal creates a `MTLDevice` for each GPU."
2. Library and function: the compiler "compiles the `add_arrays` function and adds it to a default Metal library". The function object "is a proxy for the MSL function, but it's not executable code."
3. Pipeline: "You convert the function into executable code by creating a pipeline." At that point "the device object finishes compiling the function for this specific GPU."
4. Command queue: "To send work to the GPU, you need a command queue."
5. Buffers: the arrays. The sample "uses shared memory, which both the CPU and GPU can access", which is day 1's unified memory seen from the code.
6. Command buffer and encoder: "Ask the command queue to create a command buffer", then "a compute command encoder, which encodes a compute pass."
7. Dispatch, commit, wait: the encoder is told how many threads to run, and "Metal subdivides the grid into smaller grids called threadgroups." Then "Run the commands in the command buffer by committing the command buffer to the queue", after which "Metal asynchronously prepares the commands for execution" and the CPU waits for the result.

Apple's compute tech talk gives the same picture in four sentences: "The top layer is the command queue." "The commands are batched up on the CPU through a command buffer." "To put instructions into the command buffer, we'll need a command encoder." And the one line that separates compute from graphics: "There's a graphics encoder for 3D draws, a blit encoder for copying resources around, but for this talk, we'll focus on the compute encoder for kernel dispatches" ([tech talk 10580](https://developer.apple.com/videos/play/tech-talks/10580/)).

**Apple's answer to tensor cores.** NVIDIA GPUs have separate units that multiply whole matrices per instruction. Apple's equivalent is a language feature: "Metal supports a matrix type simdgroup_matrix<T,Cols,Rows> … Operations on SIMD-group matrices are executed cooperatively by threads in the SIMD-group", where T is half, bfloat, or float and "Cols and Rows are 8" (MSL specification 4.1). An 8 by 8 tile is multiplied by the 32 threads of a simdgroup together. MLX's matrix kernels are built from exactly that: `static_assert(kFragRows_ == 8, "Only 8 x 8 fragment matrices are currently supported");` ([MLX steel mma.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/steel/gemm/mma.h)). metal-benchmarks, written in the M1 era, put it this way: "Apple's 'tensor core' is the `simdgroup_matrix` instruction, which decreases register pressure and improves ALU utilization in existing FP32 pipelines." That was before the M5 put a Neural Accelerator in every core; Metal 4 now reaches those through tensor APIs and the new Metal Performance Primitives, "the Metal Performance Primitives (MPP) framework for authoring machine learning kernels that leverage GPU neural accelerators in the Apple M5 chip" ([MPP guide, March 2026](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)).

**The advice that contradicts CUDA instinct.** The same MPP guide tells experienced GPU programmers two things they will not expect. "Theadgroup [sic] memory staging isn't necessary for the most optimized GEMM kernels. The on-chip memory hierarchy works best when you directly access device memory and allow the different levels of caching to work as designed." And "Kernels don't require any explicit software pipelining to overlap memory and compute operations. Metal achieves this execution overlap naturally with sufficient thread occupancy on each core." CUDA matrix-multiply tutorials teach both staging and pipelining as core steps. A community port of NVIDIA's shared-memory tiled kernel to Metal reached "roughly 1/2 the performance of Apple's optimized GPU `MPSMatrixMultiplication` kernel on an M1 Max" ([bkvogel/metal_performance_testing](https://github.com/bkvogel/metal_performance_testing)). The lesson is not that the port was bad. It is that the Apple core, with its large registers and dynamic caches from day 2, wants a different shape of kernel, and Apple has now said so in writing.

## Numbers to remember

| | |
|---|---|
| MSL base | C++17 with restrictions |
| The seven objects | device, library and function, pipeline, queue, buffers, command buffer and encoder, dispatch and commit |
| simdgroup_matrix | 8 by 8 tiles, multiplied by all 32 threads of a simdgroup |
| MPP guide date | 2026-03-16, the first Apple-written GEMM tiling advice |
