# Week 1, day 3 · Metal, the path from source to GPU

**Why this day.** Metal is the only door into the GPU. Even when MLX hides it, every kernel you direct goes through the same objects in the same order, and when something is slow or wrong you need to know which step it lives in. Today you read a complete kernel, in C and then in Metal, and follow it through every object to the result.

## How it works

**What Metal is.** Metal is Apple's programming interface for the GPU. It covers graphics and calculation; this course only uses the calculation side, called compute. The functions that run on the GPU are written in the Metal Shading Language, MSL, which Apple describes as "a variant of C++ designed for GPU programming" and the specification pins down: "In Metal 4 and later, the Metal programming language is a C++17-based specification with extensions and restrictions" ([MSL specification 4.1](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)). A GPU function that does calculation is a kernel: "A compute function (also called a kernel) is a data-parallel function that is executed over a 1-, 2-, or 3D grid." Apple's word for any GPU function is shader, "because historically they were first used to calculate colors in 3D graphics" ([Performing Calculations on a GPU](https://developer.apple.com/documentation/metal/performing-calculations-on-a-gpu)). The name means nothing here.

**The kernel, in C and in MSL.** Apple's sample adds two arrays. On the CPU:

```c
void add_arrays(const float* inA,
                const float* inB,
                float* result,
                int length)
{
    for (int index = 0; index < length ; index++)
    {
        result[index] = inA[index] + inB[index];
    }
}
```

The same work as a Metal kernel:

```metal
kernel void add_arrays(device const float* inA,
                       device const float* inB,
                       device float* result,
                       uint index [[thread_position_in_grid]])
{
    // the for-loop is replaced with a collection of threads, each of which
    // calls this function.
    result[index] = inA[index] + inB[index];
}
```

Both listings are verbatim from Apple's article. Read the differences, because they are the whole language in miniature. `kernel` marks a function the GPU can launch over a grid; "Functions declared with the kernel or [[kernel]] attribute must return void." The loop is gone: "The MSL version removes the for-loop from the C version because the GPU calls the function with multiple threads in the compute grid." The loop counter became an argument, `uint index [[thread_position_in_grid]]`, which "declares that Metal should calculate a unique index for each thread and pass that index in this argument." And every pointer carries a word, `device`: "Whenever you declare a pointer in MSL, you need to supply a keyword to declare its address space. Use the `device` address space to declare persistent memory that the GPU can read from and write to." Day 5 covers the other address spaces.

**The seven objects, in order.** This is the path every launch takes. Apple's sentences for each:

1. **Device.** "Metal creates a `MTLDevice` for each GPU." On a Mac there is one.
2. **Library and function.** The compiler "compiles the `add_arrays` function and adds it to a default Metal library". The function object "is a proxy for the MSL function, but it's not executable code."
3. **Pipeline state.** "You convert the function into executable code by creating a pipeline." At that point "the device object finishes compiling the function for this specific GPU." Two compile steps: one to a portable form, one to this chip's machine code.
4. **Command queue.** "To send work to the GPU, you need a command queue."
5. **Buffers.** The arrays. "The sample app uses shared memory, which both the CPU and GPU can access": yesterday's unified memory, as seen from code.
6. **Command buffer and encoder.** "Ask the command queue to create a command buffer", then "a compute command encoder, which encodes a compute pass." The encoder is told the pipeline, the buffers, and the thread count. "Metal subdivides the grid into smaller grids called threadgroups."
7. **Commit and wait.** "Run the commands in the command buffer by committing the command buffer to the queue." Then "Metal asynchronously prepares the commands for execution" and the CPU waits until the GPU reports done.

Apple's compute talk compresses the same path: "The top layer is the command queue." "The commands are batched up on the CPU through a command buffer." "To put instructions into the command buffer, we'll need a command encoder." And the line that separates compute from graphics: "There's a graphics encoder for 3D draws, a blit encoder for copying resources around, but for this talk, we'll focus on the compute encoder for kernel dispatches" ([tech talk 10580](https://developer.apple.com/videos/play/tech-talks/10580/)).

```
source (MSL) → library → function → pipeline state (compiled for this GPU)
                                          │
buffers (your arrays) ──────┐             │
                            ▼             ▼
command queue → command buffer → compute encoder: set pipeline, set buffers, dispatch grid
                      │
                   commit ──────► GPU runs ──────► CPU waits ──────► read result
```

**Where time goes on this path.** Steps 1 to 4 happen once per program. Step 5 happens once per array. Steps 6 and 7 happen on every launch, and they are the launch cost from week 2 and week 3 day 5: in the first version of this course, one round trip through this path measured about 195 microseconds on an M5 through MLX, and about 450 after the GPU had sat idle for 20 milliseconds. A kernel that moves 32 MB needs about 270 microseconds of memory time on an M5, so for small kernels the path costs more than the work.

## Apple's answer to tensor cores

NVIDIA GPUs have separate units that multiply whole matrices per instruction. Apple's equivalent, until the M5, was a language feature: "Metal supports a matrix type simdgroup_matrix<T,Cols,Rows> … Operations on SIMD-group matrices are executed cooperatively by threads in the SIMD-group", where T is half, bfloat, or float and "Cols and Rows are 8" (MSL specification 4.1). An 8 by 8 tile is loaded, multiplied, and stored by the 32 threads of a simdgroup acting together. MLX's matrix kernels are built from exactly these: `static_assert(kFragRows_ == 8, "Only 8 x 8 fragment matrices are currently supported");`, with each of the 32 lanes holding 2 of the 64 elements ([MLX steel mma.h](https://raw.githubusercontent.com/ml-explore/mlx/main/mlx/backend/metal/kernels/steel/gemm/mma.h)). metal-benchmarks, written in the M1 era, judged it: "Apple's 'tensor core' is the `simdgroup_matrix` instruction, which decreases register pressure and improves ALU utilization in existing FP32 pipelines." The M5 added real accelerators in every core; day 7 covers how Metal 4 reaches them.

## The advice that contradicts CUDA instinct

Apple's 2026 guide for the M5 tells experienced GPU programmers two things they will not expect. "Theadgroup [sic] memory staging isn't necessary for the most optimized GEMM kernels. The on-chip memory hierarchy works best when you directly access device memory and allow the different levels of caching to work as designed." And "Kernels don't require any explicit software pipelining to overlap memory and compute operations. Metal achieves this execution overlap naturally with sufficient thread occupancy on each core" ([MPP guide, March 2026](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)). CUDA matrix tutorials teach both as core steps. A community port of NVIDIA's tiled kernel to Metal reached "roughly 1/2 the performance of Apple's optimized GPU `MPSMatrixMultiplication` kernel on an M1 Max" ([bkvogel/metal_performance_testing](https://github.com/bkvogel/metal_performance_testing)). Yesterday's core explains it: with little scratch and dynamic caches, the staging rung costs barriers and buys nothing.
