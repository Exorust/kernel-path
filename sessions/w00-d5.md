# w00-d5 · What makes a kernel slow

**After today you can say:** a kernel is always waiting on one of three things: memory, math, or the launch. Memory time is bytes divided by memory speed. A launch costs about 0.2 milliseconds on this Mac before any byte moves. And a GPU with too few threads in flight cannot hide the wait for memory, so the same work runs many times slower.

**Words you will meet.**
- *Bandwidth*, or memory speed: how many bytes per second memory can deliver. About 115 to 120 GB/s on this M5, measured.
- *Roof*: the best this machine can do on bytes per second. Every kernel's score is its percent of the roof.
- *Memory-bound*: the kernel's time is set by moving bytes. *Compute-bound* or math-bound: set by arithmetic.
- *Launch cost*: the fixed time to get a kernel started and get the result back, however small the array.
- *Latency*: the wait between asking memory for a value and getting it, hundreds of cycles.
- *Latency hiding*: while one simdgroup waits for memory, the core runs another. It needs many simdgroups in flight.

## Read (15 minutes)

**Main.** Horace He, *Making Deep Learning Go Brrrr From First Principles*: https://horace.io/brrr_intro.html You read it in the TTFT roadmap; read it again now with one purpose. Read the intro with its three parts, compute, memory bandwidth, overhead; then "Memory Bandwidth" through "Reasoning about Memory-Bandwidth Costs"; then "Overhead". Skim the matmul part of "Compute". The one worked number to keep: "an A100 has 1.5 terabytes/second of global memory bandwidth, and can perform 19.5 teraflops/second of compute. So, if you're using 32 bit floats (i.e. 4 bytes), you can load in 400 billion numbers in the same time that the GPU can perform 20 trillion operations." The GPU does about 50 operations per number loaded before memory stops being the limit. The numbers for your M5 are smaller, the shape of the argument is the same.

**Pair with it, for the part Horace skips.** Khronos Vulkan tutorial, *Occupancy and Latency Hiding: Keeping the GPU Busy*: https://docs.vulkan.org/tutorial/latest/Advanced_Vulkan_Compute/02_Compute_Architecture/03_occupancy_and_latency_hiding.html Whole page, 5 minutes. Its words are Vulkan's: a "workgroup" is a threadgroup, an "invocation" is a thread, a "CU" is a GPU core. "fetching a single piece of data from VRAM can take hundreds or even thousands of clock cycles." That is why a core keeps many simdgroups resident and switches between them.

**Two-minute add-ons.** Modal GPU Glossary, *Little's law*: https://modal.com/gpu-glossary/perf/littles-law "If a GPU has a peak throughput of 1 instruction per cycle and a memory access latency of 400 cycles, then 400 concurrent memory operations are needed across all active warps in a program." And *Overhead*: https://modal.com/gpu-glossary/perf/overhead for one number on launch cost on NVIDIA, "on the order of 10 μs per kernel launch". On this Mac through MLX it is about 200 microseconds, measured; the two numbers differ because MLX's path includes Python and a wait for the result.

## Code to read (8 minutes)

Three finished files. Each prints the arithmetic and the measurement side by side, on this Mac, today. Run them in this order.

- **`kernels/w00/day5_launch_cost.py`.** Rule 1, time = bytes / memory speed, holds for 128 MB and 512 MB and is off by thousands of times for 8 KB. Rule 2 adds the launch cost and lands within about 10 percent. It also shows the launch cost is not a constant: about 195 microseconds when launches follow each other, about 450 after a 20 millisecond pause.
- **`kernels/w00/day5_waiting_on.py`.** Three experiments, each changing one thing by 4 times: bytes, math, or nothing but a tiny array. The time follows the thing the kernel waits on. Then it predicts a new kernel's time from both rules before running it.
- **`kernels/w00/day5_rowsum.py`.** The sum of every row of a 2,000 by 4,000 matrix: one simdgroup per row, the kernel week 1 Wednesday builds with a multiply added. It predicts the time, measures it, prints the line every later session prints and explains each field, then runs the same 32 MB as 2 rows of 4,000,000 and shows it 50 to 60 times slower with 64 threads.

The numbers on your run will differ from the ones in these notes by some percent. The laptop is never idle: the terminal app and the browser use the GPU too. A line at the end of each file says if a timing moved while it was being measured.
