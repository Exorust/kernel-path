# w00-d3 · How Apple's GPU organizes threads and memory

**After today you can say:** threads run in groups of 32 called simdgroups, simdgroups are bundled into threadgroups, a threadgroup goes to one GPU core, and there are three places a value can live.

**Words you will meet.**
- *Grid*: all the threads of one launch, arranged in 1, 2 or 3 dimensions. You choose its size.
- *Threadgroup*: a bundle of threads that is sent to one GPU core together and can share a small scratch memory. You choose its size, at most 1,024.
- *Simdgroup* (Apple writes SIMD-group): 32 threads that execute the same instruction at the same moment. Fixed at 32 on every Apple GPU.
- *Lane*: a thread's place inside its simdgroup, 0 to 31.
- *simd_sum*: adds one value across the 32 lanes and gives every lane the total.
- *Threadgroup memory*: the scratch memory one threadgroup shares. At most 32 KB.
- *Barrier*: a point where every thread of a threadgroup waits for the others, so that what one wrote to scratch memory is visible to all.
- *Occupancy*: how many simdgroups a core keeps resident at once.

## Read (15 minutes)

**Main.** Apple, *Creating threads and threadgroups*: https://developer.apple.com/documentation/metal/creating-threads-and-threadgroups About 865 words, 6 minutes: overview, position in the grid, position in the threadgroup, SIMD groups. Its example kernel is an image filter that uses a texture; skip the texture details and keep the indexing idea. Apple's sentence to keep: "Each point in the grid represents a thread, which is a single instance of your kernel function."

**Pair with it.** Apple tech talk *Discover Metal enhancements for A14 Bionic*, transcript: https://developer.apple.com/videos/play/tech-talks/10858/ Start at "I am Swami Narayanan" and read through the array-sum walkthrough, 8 to 10 minutes. Stop before the matrix-multiply part. It explains a reduction from scratch, then threadgroups, then 32-lane SIMD groups running in lockstep, then `simd_sum`, and then sums a large array in three stages: device memory, per-simdgroup sums, a threadgroup-memory array. The sentence to keep: "simd_sum adds up values of a variable across all active threads in the SIMD group and broadcasts the sum back to all the threads." It is framed as the A14 GPU; M-series Macs are the same family.

**Backup.** The WWDC22 talk *Scale compute workloads across Apple GPUs*, transcript from about 04:55: https://developer.apple.com/videos/play/wwdc2022/10159/ Four sentences carry the numbers: "A workload is dispatched in the form of a 3D grid of threadgroups." "A single threadgroup is further broken down into SIMD-groups." "On all Apple GPUs, it is equal to 32." "Threadgroups can have up to 1024 threads per threadgroup and threads can share up to 32K of threadgroup memory."

**Your glossary.** [simdgroup](https://metalworking.vercel.app/machine/simdgroup/), [threadgroup-memory](https://metalworking.vercel.app/machine/threadgroup-memory/), [gpu-core](https://metalworking.vercel.app/machine/gpu-core/).

**The three memories, in Apple's words** (specification 4.1, section 4): a value declared inside the kernel is in the *thread* address space, "not visible to other threads"; `threadgroup` memory is what "threads in a threadgroup can work together by sharing", and it is "faster on most devices than sharing data in device memory"; `device` memory is where the arrays are. Sizes on this machine: thread memory is the register file, about 200 KB per core measured on M1 and M2 by philipturner/metal-benchmarks and not published for the M5; threadgroup memory 32 KB per threadgroup; device memory is the Mac's RAM, 32 GB here, read at about 120 GB/s.

Hold these three questions while reading:
1. If I launch 2,048 threads in threadgroups of 1,024 on a 10-core GPU, how many cores do anything?
2. After `simd_sum`, how many of the 32 threads hold the answer, and so why does only one of them store it?
3. What goes wrong if two threads of a threadgroup write to scratch memory and read each other's value with no barrier between?

## Code to read (8 minutes)

**Run `kernels/w00/day3_threads.py`.** Five finished kernels:
- A asks every thread who it is. Change `WHO` to each of the four names in the comment and `WIDTH` to 32, 64 and 128, and run after each change. That is the whole execution model, seen.
- B shows that after `simd_sum` all 32 threads hold the same total.
- C sums each group of 32 and lets only lane 0 store.
- D reverses values through shared scratch memory with a barrier. Change `SCRATCH_WIDTH` to 64 and see the reversal span change.
- E is a grid with two dimensions, which day 5's row-sum kernel and all of week 1 use.

One caution the specification itself gives: "Within a threadgroup, threads are divided into SIMD-groups in an implementation-defined fashion." The patterns part A prints are what this M5 does, measured, not a guarantee. Always ask a thread for its lane with `thread_index_in_simdgroup`; never compute it from the grid position.
