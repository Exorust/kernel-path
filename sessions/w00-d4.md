# w00-d4 · MLX custom kernels, and one real kernel read end to end

**After today you can say:** `mx.fast.metal_kernel` does all of day 1 for me. I write only the body; MLX writes the function header, compiles it, launches it, and hands back an array. Nothing runs until something asks for the result.

**Words you will meet.**
- *Body*: the inside of the kernel function. The only Metal you write in this repo.
- *Generated function*: the full MSL function MLX wraps around your body. `verbose=True` prints it.
- *Lazy evaluation*: MLX records what you asked for and runs it only when a result is needed, or when you call `mx.eval`.
- *Template parameter*: a type or whole number fixed when the kernel is compiled, such as `T` or `COLS`, passed with `template=[...]`.
- *Gated delta rule*: the update rule of the linear-attention layer that weeks 6 to 10 build a kernel for. Today you only read its existing kernel for shape, not for math.

**One real kernel, end to end.** This is the kernel that runs every linear-attention model in mlx-lm, and the one weeks 6 to 10 are about. Verbatim, the heart of `_make_gated_delta_kernel` in `mlx_lm/models/gated_delta.py`, lines 64 to 120 at commit 9d8abd9: https://github.com/ml-explore/mlx-lm/blob/9d8abd94d63a9b3c72e7e9b146e43af1005368fa/mlx_lm/models/gated_delta.py#L64-L120

```metal
        auto n = thread_position_in_grid.z;
        auto b_idx = n / Hv;
        auto hv_idx = n % Hv;
        auto hk_idx = hv_idx / (Hv / Hk);
        constexpr int n_per_t = Dk / 32;

        // q, k: [B, T, Hk, Dk]
        auto q_ = q + b_idx * T * Hk * Dk + hk_idx * Dk;
        auto k_ = k + b_idx * T * Hk * Dk + hk_idx * Dk;

        // v, y: [B, T, Hv, Dv]
        auto v_ = v + b_idx * T * Hv * Dv + hv_idx * Dv;
        y += b_idx * T * Hv * Dv + hv_idx * Dv;

        auto dk_idx = thread_position_in_threadgroup.x;
        auto dv_idx = thread_position_in_grid.y;

        // state_in, state_out: [B, Hv, Dv, Dk]
        auto i_state = state_in + (n * Dv + dv_idx) * Dk;
        auto o_state = state_out + (n * Dv + dv_idx) * Dk;

        float state[n_per_t];
        for (int i = 0; i < n_per_t; ++i) {{
          auto s_idx = n_per_t * dk_idx + i;
          state[i] = static_cast<float>(i_state[s_idx]);
        }}

        {g_comment}
        {g_setup}
        auto beta_ = beta + b_idx * T * Hv;

        for (int t = 0; t < T; ++t) {{
          if ({mask_source}) {{
            float kv_mem = 0.0f;
            for (int i = 0; i < n_per_t; ++i) {{
              auto s_idx = n_per_t * dk_idx + i;
              state[i] = state[i] * {g_access};
              kv_mem += state[i] * k_[s_idx];
            }}
            kv_mem = simd_sum(kv_mem);

            auto delta = (v_[dv_idx] - kv_mem) * beta_[hv_idx];

            float out = 0.0f;
            for (int i = 0; i < n_per_t; ++i) {{
              auto s_idx = n_per_t * dk_idx + i;
              state[i] = state[i] + k_[s_idx] * delta;
              out += state[i] * q_[s_idx];
            }}
            out = simd_sum(out);
            if (thread_index_in_simdgroup == 0) {{
              y[dv_idx] = static_cast<InT>(out);
            }}
          }} else {{
            y[dv_idx] = static_cast<InT>(0);
          }}
```

The doubled braces `{{ }}` are Python f-string escapes; the GPU sees single braces. The `{g_...}` and `{mask_source}` are Python filling in two variants of the same kernel.

The same shape in plain MSL, one head, no batch, scalar gate, no mask. This rewrite is mine, not mlx-lm's, and it drops the real kernel's generality so the structure shows:

```metal
    uint lane = thread_index_in_simdgroup;      // 32 lanes share one state row; each holds Dk/32 = 4 numbers
    uint row  = thread_position_in_grid.y;      // which row of the state this simdgroup owns
    float state[4];
    for (int i = 0; i < 4; ++i) state[i] = state_in[row * Dk + 4 * lane + i];

    for (int t = 0; t < T; ++t) {               // one token at a time: this loop is why prefill is slow
        float kv = 0.0f;
        for (int i = 0; i < 4; ++i) { state[i] *= g[t]; kv += state[i] * k[t * Dk + 4 * lane + i]; }
        kv = simd_sum(kv);                      // the row's prediction for this token
        float delta = (v[t * Dv + row] - kv) * beta[t];
        float out = 0.0f;
        for (int i = 0; i < 4; ++i) { state[i] += k[t * Dk + 4 * lane + i] * delta; out += state[i] * q[t * Dk + 4 * lane + i]; }
        out = simd_sum(out);
        if (lane == 0) y[t * Dv + row] = out;
    }
```

What to notice, and nothing more today: the state row lives in registers for the whole kernel (`float state[4]` per lane, day 3's thread memory); every token needs two `simd_sum` calls; only lane 0 stores; and the outer `for (t ...)` walks the whole sequence one step at a time, which is the thing weeks 6 to 10 replace. The three dispatch sizes are in the same file: `grid=(32, Dv, B * Hv)` and `threadgroup=(32, 4, 1)`, so `.x` is the lane, `.y` the state row, `.z` the batch and head.
