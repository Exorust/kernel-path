# w00-d2 · MSL, the language

**After today you can say:** MSL is C++17 with things removed. I can read a kernel body and say what each line does.

**Words you will meet.**
- *Literal*: a number written in code. `1.0f` is a float, `1` is a whole number.
- *Cast*: converting a value from one type to another, written `float(i)`.
- *Address space*: the kind of memory a pointer points into. Every pointer in MSL names one.
- *Attribute*: the `[[...]]` label on a function argument that tells Metal what to put there.
- *Built-in function*: one Metal provides, such as `sqrt` or `exp`. There is no standard library.
- *float4*: four floats held together, with parts `.x .y .z .w`.

### MSL in one page

**What it is.** The specification says: "In Metal 4 and later, the Metal programming language is a C++17-based specification with extensions and restrictions." If you can read C, you can read a kernel body. Variables, arithmetic, `if`, `for`, `while`, the ternary `? :`, arrays, pointers and casts all work as in C.

**Numbers.** The types you will use: `float` (32-bit), `half` (16-bit), `int` and `uint` (32-bit whole numbers, `uint` never negative), `bool`. Also `short`, `ushort`, `uchar`, and from Metal 3.1 `bfloat`. There is no `double`: the specification states "Metal does not support the double, long long, unsigned long long, and long double data types." Write float literals with an `f`: `0.5f`. A literal with an `h` is a half. Whole-number division drops the remainder, `7 / 2` is `3`, and `%` gives the remainder. A `uint` that goes below zero wraps around to a huge number, which is a common bug.

**Vectors.** `float2`, `float3`, `float4`, and the same for `half`, `int`, `uint`. Arithmetic on a vector acts on every part. You will use `float4` and `half4` to read four values from memory in one load.

**Casts.** `float(i)` or `(float)i`. Converting `half` to `float` before doing math and back after is the normal pattern in this repo.

**Functions that exist.** `sqrt`, `exp`, `log`, `abs`, `min`, `max`, `clamp`, `fma`, `dot`, and the simdgroup ones from day 3 such as `simd_sum`. They are in a namespace called `metal`; inside an MLX kernel body you may call them bare, `exp(x)`, or qualified, `metal::exp(x)`.

**What does not exist.** No `printf` (to see a value, write it into an output array). No `new` or `malloc`. No exceptions, no virtual functions, no derived classes, no `goto`. No C++ standard library: the specification says "Do not use the C++ standard library in Metal code. Instead, Metal has its own standard library."

**Three memories, by name.** Every pointer says where it points. From section 4:
- `device`: "buffer memory objects allocated from the device memory pool that are both readable and writeable". Your arrays.
- `threadgroup`: memory that "threads in a threadgroup can work together by sharing". Small and fast. Day 3.
- `thread`: "the per-thread memory address space. Variables allocated in this address space are not visible to other threads. Variables declared inside a graphics or kernel function are allocated in the thread address space." Every `float x` you write inside a kernel is this. In practice it is a register.

**The function header, read once.** `[[kernel]] void name(const device float* a [[buffer(0)]], device float* out [[buffer(1)]], uint3 thread_position_in_grid [[thread_position_in_grid]])`. The `[[...]]` parts are attributes. `[[buffer(0)]]` ties `a` to the first array passed in. `[[thread_position_in_grid]]` asks Metal to fill in this thread's position. In MLX you never write this header; day 4 shows MLX writing it for you.

**One real kernel from MLX itself.** This is how MLX applies any single-input operation, such as `exp`, to a whole array. Verbatim from `mlx/backend/metal/kernels/unary.h`, lines 3 to 18 at commit 3c40e8f: https://github.com/ml-explore/mlx/blob/3c40e8f92d0cce0866fc2f436f9b5096cf3b0ea7/mlx/backend/metal/kernels/unary.h#L3-L18

```metal
template <typename T, typename U, typename Op, int N = WorkPerThread<T>::n>
[[kernel]] void unary_v(
    device const T* in,
    device U* out,
    constant uint& size,
    uint index [[thread_position_in_grid]]) {
  index *= N;
  if (N > 1 && index + N > size) {
    for (int i = 0; index + i < size; ++i) {
      out[index + i] = static_cast<U>(Op()(in[index + i]));
    }
  } else {
    for (int i = 0; i < N; ++i) {
      out[index + i] = static_cast<U>(Op()(in[index + i]));
    }
  }
}
```

The same thing with the templates taken out, for `exp` on floats with each thread doing 4 elements. This rewrite is mine, not MLX's:

```metal
[[kernel]] void unary_v(device const float* in, device float* out, constant uint& size,
                        uint index [[thread_position_in_grid]]) {
  index *= 4;                                   // thread t handles elements 4t to 4t + 3
  if (index + 4 > size) {                       // the last thread may run off the end
    for (int i = 0; index + i < size; ++i) out[index + i] = exp(in[index + i]);
  } else {
    for (int i = 0; i < 4; ++i) out[index + i] = exp(in[index + i]);
  }
}
```

What to notice: `template <typename T, ...>` lets one kernel serve every type; `Op()(x)` is "apply the operation"; `constant uint& size` is a single number passed in, in the read-only `constant` memory; and the `if` exists only because the array length may not divide by 4.
